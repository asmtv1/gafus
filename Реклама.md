# Rewarded Ads Credits Implementation Plan

## Summary

Реализуем единую механику rewarded credits для web и mobile:

- `1 rewarded ad event` пополняет баланс до `5` кредитов.
- Максимальный баланс, который можно набрать рекламой: `5`.
- Refund credits не должны сгорать: возвраты хранятся отдельно, если основной баланс уже полон.
- Расход:
  - статья: `1` кредит;
  - открытие содержательного шага в дне: `1` кредит;
  - бронирование консультации: `5` кредитов.
- Premium всегда имеет приоритет: если у пользователя активная подписка, кредиты не списываются.
- Кредиты работают только внутри Gafus, не имеют денежной ценности и не конвертируются в деньги.
- Вся критичная бизнес-логика живет в `@gafus/core`; web/mobile/admin остаются тонкими клиентами.
- Реклама:
  - mobile: `yandex-mobile-ads` / Yandex Mobile Ads React Native SDK 8 + Yandex Mobile Mediation;
  - web: Yandex Advertising Network rewarded units для сайтов.

## Review: Что исправлено в исходном плане

1. **Клиентский `grant` был слишком доверенным.**
   Исходный план предполагал, что клиент после `onRewarded` просто вызывает `/grant`. Это можно подделать без просмотра рекламы. Исправление: добавить серверную ad-сессию с nonce/TTL/idempotency, хранить lifecycle events и начислять только по валидной незавершенной сессии. Полностью доказать просмотр без server-side verification от провайдера нельзя, поэтому риск дополнительно режется дневным лимитом, cap баланса, rate limit и аудитом.

2. **`GET /training/day` уже отдает весь контент шага.**
   Если просто списывать кредит при start/complete, пользователь сможет открыть день и прочитать шаги без списания. Исправление: добавить redacted locked-step DTO и явный `POST unlock` перед раскрытием шага. Сервер также должен защитить media URL, PDF, offline-download и step action endpoints.

3. **Для статей текущий `getArticleBySlug` не учитывает Premium/credits как источник доступа к `content`.**
   Сейчас сервис возвращает `content` только для `PUBLIC` или `ArticleAccess`. Если статья закрыта, одна замена `requireWebAppSubscriptionOrThrow` не откроет контент. Исправление: добавить article access helper, который явно решает, можно ли вернуть `content` по Premium, существующему ArticleAccess или rewarded unlock.

4. **Списание на GET создает побочные эффекты и риск повторов.**
   Исправление: для статей и шагов использовать явный unlock endpoint. GET возвращает контент только если цель уже доступна; POST unlock списывает идемпотентно.

5. **Баланс `max=5` конфликтует с `dailyAdLimit=2/3`.**
   Если баланс уже `5`, смотреть рекламу нельзя. Если баланс `1-4`, сервер может пополнить только недостающую часть до `5`; UI должен говорить "пополнить баланс до 5", а не обещать ровно 5 новых кредитов. `dailyAdLimit` имеет смысл, когда пользователь тратит кредиты между просмотрами.

6. **Бронирование консультации требует reserve/refund flow.**
   Нельзя просто списывать после `bookSlot`: Telemost, SLA, idempotency replay и отмены создают частичные состояния. Исправление: делать списание/резерв через core wrapper с idempotency key и гарантированным refund на системные/тренерские/пользовательские отмены по продуктовой политике.

7. **Web rewarded у Яндекса имеет внешний prereq.**
   Rewarded units для сайтов требуют доступа через поддержку, а desktop и touch блоки создаются отдельно. Это блокер до разработки web CTA.

8. **Mobile SDK требует native rebuild.**
   `yandex-mobile-ads` не приедет OTA-обновлением Expo. Нужны dev/release builds, проверка Android/iOS native requirements, placement IDs и privacy disclosures.

9. **Analytics allowlist строгий.**
   Недостаточно просто отправить новые события: нужно расширить `packages/types/src/analytics.ts` и `packages/analytics/src/validate.ts`, иначе события будут отброшены.

10. **Нужно сохранить существующие ownership/access checks.**
    Credits не должны обходить приватные курсы, роли, ownership и staff permissions. Они заменяют только проверку "есть Premium для платного действия", а не базовую авторизацию.

11. **Refund при полном балансе мог сгореть.**
    Если пользователь потратил `5` кредитов на консультацию, потом снова набрал баланс до `5`, а консультация отменилась, простой refund "не выше cap" потерял бы ценность возврата. Исправление: добавить `pendingRefundCredits` в wallet. Возврат сначала пополняет balance до `5`, остаток кладется в pending refund и автоматически применяется после следующих списаний.

12. **Rewarded unlock влияет не только на detail endpoints.**
    Шаг может включать exam, survey, video report, notifications и signed media routes. Если открыть только `training/step/start`, пользователь упрется в соседние endpoints. Исправление: добавить surface matrix и обязательный audit всех `requireWebAppSubscription*` call sites.

### Balance Rules

- Wallet создается лениво при первом status/grant/spend.
- `balance` всегда `0..5`.
- `pendingRefundCredits` всегда `>= 0` и хранит возвраты, которые не поместились в `balance`.
- `grantAmount = min(5, 5 - currentBalance)`.
- Если `currentBalance === 5`, `canWatchAd = false`, reason `BALANCE_FULL`.
- Если `currentBalance === 0`, UI может писать "получите 5 кредитов".
- Если `currentBalance` от `1` до `4`, UI пишет "пополните баланс до 5"; сервер возвращает фактический `grantedCredits`.
- Дневной лимит считается по успешным `EARN` транзакциям за московский календарный день.
- Дневной лимит увеличивается только после успешного начисления `grantedCredits > 0`.
- Перед status/spend/grant сервер вызывает `applyPendingRefundCredits`: переносит из `pendingRefundCredits` в `balance` все, что помещается до `5`.

### Refund Rules

- Refund never drops value.
- Если `balance + refundAmount <= 5`, весь refund идет в `balance`.
- Если `balance + refundAmount > 5`, часть до cap идет в `balance`, остаток идет в `pendingRefundCredits`.
- Spend сначала списывает из `balance`, затем снова вызывает `applyPendingRefundCredits`, чтобы pending refund стал доступен для следующего действия.
- Пока `balance === 5`, реклама недоступна, даже если `pendingRefundCredits > 0`.
- UI status должен показывать `pendingRefundCredits`, чтобы пользователь видел, что возврат не потерян.

### Access Rules

- Premium active: доступ разрешен, credits не списываются.
- Existing ownership/access checks выполняются раньше rewarded access:
  - auth required;
  - course access;
  - private/admin/trainer permissions;
  - consultation slot and role checks;
  - article visibility/business rules.
- Credits не дают глобальный Premium и не включают офлайн-скачивание всего курса.
- Credits открывают конкретную цель:
  - `ARTICLE:{articleId}`;
  - `COURSE_STEP:{stepOnDayId}`;
  - `DAILY_COURSE_STEP:{scheduleId}:{bundleStepId}`;
  - `CONSULTATION_BOOKING:{clientId}:{idempotencyKey}`.
- Повторное открытие уже разблокированной цели не списывает повторно.

### Rewarded Scope Matrix

Rewarded credits заменяют только Premium gate для явно перечисленных действий:

- **Article detail**: доступ к закрытому content конкретной статьи.
- **Article interaction**: like/view разрешены для public, Premium или rewarded-unlocked article.
- **Regular course step**: раскрытие содержимого конкретного `StepOnDay`.
- **Step child endpoints**: start/pause/resume/reset/complete, exam submit, survey response, video report, written feedback и step notifications разрешены только для Premium или unlocked target step.
- **Daily course step**: раскрытие и step child endpoints конкретного `scheduleId + bundleStepId`.
- **Consultation booking lifecycle**: booking, `my bookings`, cancellation and join/detail endpoints должны работать для пользователя, который создал booking через credits.

Premium-only surfaces остаются Premium-only и не открываются rewarded credits:

- full offline course download/version/updates;
- питомцы, документы питомца, профилактика, избранные курсы и другие app-wide Premium функции;
- admin/trainer/moderator tools;
- любые bulk export/download endpoints.

Каждый найденный endpoint должен попасть в одну из категорий:

- `REWARDED_ELIGIBLE_TARGET`;
- `PREMIUM_ONLY`;
- `PUBLIC_OR_EXISTING_ACCESS`;
- `STAFF_ONLY`.

### Monetized Step Types

Списывать `1` кредит за открытие содержательных шагов:

- `TRAINING`;
- `PRACTICE`;
- `THEORY`;
- `EXAMINATION`;
- `SURVEY`.

Не списывать за сервисные шаги, если продукт не решит иначе:

- `BREAK`;
- `DIARY`.

Причина: пользователь не должен платить за перерыв или форму дневника без отдельной ценности.

### Core Invariants

- Клиент никогда не передает `amount` для grant.
- Client-provided `targetType/targetId` нельзя слепо принимать для domain unlock; route сначала резолвит target из slug/dayOnCourseId/stepIndex/scheduleId.
- Все изменения wallet + ledger выполняются в `prisma.$transaction`.
- Spend:
  - сначала проверяет существующий `idempotencyKey`;
  - если transaction уже есть, возвращает replay без повторного списания;
  - если Premium активен, возвращает `skippedDueToPremium`;
  - если balance недостаточен, бросает `RewardedCreditsRequiredError`.
- Grant:
  - проверяет session owner;
  - проверяет nonce hash;
  - проверяет `expiresAt`;
  - проверяет status not granted;
  - проверяет platform settings;
  - проверяет daily limit внутри той же transaction/lock, где начисляет credits;
  - проверяет `balance < 5`;
  - создает `EARN` transaction с `idempotencyKey = rewarded:earn:{sessionId}`.
- Refund:
  - идемпотентен;
  - не теряет credits при полном `balance`;
  - переносит overflow в `pendingRefundCredits`;
  - не возвращает больше исходного spend;
  - пишет `REFUND` transaction.

### Race Condition Strategy

- Для grant/spend/refund использовать transaction + conditional wallet update.
- В начале каждой wallet transaction создать/залочить wallet row через `upsert` + row lock или PostgreSQL advisory transaction lock по `userId`.
- Daily limit check делать под тем же per-user lock, иначе две параллельные grant transaction могут обе увидеть свободный лимит.
- `recordRewardedAdEvent` не является security boundary: client-origin events нужны для аудита и funnel analytics, но не доказывают реальный просмотр.
- Для spend:
  - вызвать `applyPendingRefundCredits`;
  - `wallet.updateMany({ where: { userId, balance: { gte: amount } }, data: { balance: { decrement: amount } } })`;
  - если `count === 0`, insufficient credits;
  - затем создать ledger transaction с unique idempotency key.
  - после spend снова вызвать `applyPendingRefundCredits`, чтобы pending refund стал доступен.
- Для grant:
  - session переводить в `GRANTED` только один раз;
  - если unique transaction уже есть, вернуть replay;
  - wallet update должен учитывать cap.
- Для unlock:
  - target unlock определяется наличием `SPEND` transaction по `idempotencyKey = rewarded:spend:{userId}:{targetType}:{targetId}`.

  - генерирует `requestNonce`;
  - хранит hash nonce, не raw nonce;
  - TTL 10 минут;
  - возвращает raw nonce клиенту один раз.
- `recordRewardedAdEvent`:
  - проверяет owner;
  - пишет `RewardedAdEvent`;
  - переводит status только вперед по lifecycle.
- `grantRewardedCredits`:
  - проверяет owner + nonce;
  - если expired, status `EXPIRED`;
  - если session уже `GRANTED`, возвращает idempotent result;
  - если event `REWARDED` не записан, можно принять grant, но обязательно записать synthetic `REWARDED` с providerPayload;
  - создает `EARN` transaction.

Security note:

- На текущих официальных React Native rewarded docs Yandex публично описывает client callbacks (`onRewarded`) как сигнал награды, а не server-side verification. Поэтому `grant` остается low-trust endpoint и не должен выдавать деньги, скидки или другие high-value rewards.
- Если у Yandex будет доступен server-side verification/callback для rewarded, добавить provider verification hook до public rollout. До этого держать cap low и мониторить suspicious grants.
- Events endpoint не должен повышать доверие к grant: злоумышленник может отправить forged lifecycle events так же, как forged grant.

### 19. Security and Abuse Review

Threats:

- forged grant endpoint;
- replayed session/nonce;
- parallel grant race exceeding daily limit;
- racing grant/spend requests;
- client passing arbitrary amount;
- web client selecting mobile platform/placement;
- client unlocking target it should not access;
- generic status endpoint leaking whether arbitrary target IDs exist;
- reading locked step content from GET day;
- fetching video/PDF/image URLs for locked step;
- offline download bypass;
- exam/survey/report/notification endpoints bypassing step unlock;
- credit-booked consultation inaccessible because `my/cancel/join` stayed Premium-only;
- user farming consultation refunds;
- refund value dropped when balance is already full;
- adblock/no-fill causing broken paywall;
- provider placement IDs missing or wrong per platform.

Mitigations:

- server-created sessions;
- nonce hash + TTL;
- one active session per user/platform/target;
- per-user wallet lock for grant/spend/refund and daily limit check;
- unique idempotency keys;
- platform settings and placement validation;
- platform constrained by route context;
- no client amount;
- domain resolvers before unlock;
- target status only through domain resolvers, not raw arbitrary IDs;
- redacted locked DTO;
- media URL access checks;
- child endpoint access helpers for exam/survey/report/notifications;
- consultation lifecycle ownership checks for credit-booked users;
- pending refund credits;
- strict rate limits on session/grant/unlock;
- low balance cap;
- daily limit;
- admin flags default off;
- monitoring suspicious grant-to-show ratio;
- focused security scan before release.

  - set `paywallCtaEnabled=false`;

  - disable all platforms;

  - audit `RewardedCreditTransaction` and `RewardedAdSession`.

  - mobile: remote disable via settings; SDK remains installed but unused;
