# Chat2: **только proxy-only** / обязательное обновление iOS и Android

**Актуальное решение владельца 05.11.2026:** iOS/Android 1.7.3 загружены в магазины и находятся на ревью. Серверный CI/CD не ожидает их публикации, не требует store attestation и не проверяет публичную mobile policy. Проверки независимых серверных секретов, proxy ACL, QA и реального runtime сохраняются. Описание прежнего порядка публикации ниже — историческое; его требования к блокировке серверного релиза отменены этим решением.

**Решение владельца, 05.11.2026:** старого режима Chat2, поддержки старых Mobile и подписок на комнату по JWT **не будет**. Все обязаны перейти на новую версию приложения. Этот документ — порядок реального выпуска, **не разрешение на deploy**. Текущие изменения выполнялись только в локальном `gafus-refactor`, без изменения GitHub Secrets, production БД, Cloud.ru, брокера или магазинов приложений.

## Security contract

- `GET /api/v1/chats/realtime/connect` выдаёт JWT **только для установления WebSocket-соединения** и `subscriptionMode: "proxy"`. При неготовом broker→Hono proxy сервер отвечает `503`, а не старым режимом. `GET /api/v1/chats/:id/realtime` **удалён**. Web/Mobile передают в `newSubscription` пустые `{}`, а не `token` или `getToken`.
- Centrifugo namespace `chat2`: `subscribe_proxy_enabled=true`; API `POST /internal/chat2/chat2-subscribe` (брокер → Hono) принимает только собственный статический секрет брокера, затем **заново вызывает `readGate`** из БД для комнаты и пользователя. Неуспех ACL, BAN, несуществующая комната, отказ БД/прокси: **запрет подписки** (fail-closed).
- ВНИМАНИЕ: Centr​ifugo сначала проверяет комнатный subscription JWT, если его передал клиент, и может обойти proxy. Поэтому `client.subscription_token.enabled=true`, но HMAC `CENTRIFUGO_CLIENT_SUBSCRIPTION_TOKEN_HMAC_SECRET_KEY` **специально отдельный, никогда никем не используемый для подписания**, issuer `gafus-chat2-subscription-deny`; он нужен **для отказа старому токену**, а не для его выдачи. Нельзя ставить старый connection signing secret в этот слот и нельзя выключать отдельную проверку. См. `infra/chat2/centrifugo.prod.json` и проверку реальным E2E.
- **Четыре независимых секрета (не копировать значения):** `CHAT2_CENTRIFUGO_TOKEN_SECRET` — connection JWT; `CHAT2_CENTRIFUGO_API_KEY` — server-to-broker unsubscribe/publish; `CHAT2_SUBSCRIBE_PROXY_SHARED_SECRET` — broker-to-Hono HMAC-like shared header; `CHAT2_CENTRIFUGO_SUBSCRIPTION_SECRET` — никогда не выдаваемый HMAC-верификатор отказа старым room JWT. Все случайные, длинные, только серверные, не в сборке клиента/логах. Release gate отклоняет пропуски и совпадающие секреты.
- На внешних `gafus.ru`/Vite Nginx `/internal/*` отдаёт `404`. **Критично:** на отдельном публичном `api.gafus.ru` запрещён **только** `/internal/chat2/chat2-subscribe*` (404), чтобы не перекрыть другие аутентифицированные Cloud.ru media-job callbacks. Внутри Docker браузеру открыт только `/connection/websocket`, служебный API Centrifugo не публикует порт.
- При `BAN`/`KICK` или DM block сначала **коммитится запрет в БД**, затем выполняется Centrifugo `/api/unsubscribe`. Такой порядок запрещает повторное подключение между unsubscribe и фиксацией BAN. Broker outage может отложить немедленный отзыв уже живого socket: ошибка возвращается, новое подключение БД заблокирует. Для операционной надёжности требуется мониторить `CHAT2_REALTIME_REVOKE_FAILED` и обеспечить ручное/автоматическое повторное отключение без возврата JWT; это отдельный операционный follow-up.

## Принудительное обновление, без legacy exception

1. **Сначала** построить и опубликовать **новые** подписанные production Mobile в App Store и Android магазине(ах), подтвердить их доступность для пользователей. Последняя видимая в исходниках **старая** версия `apps/mobile/app.json` — `1.7.2`, она **не является** версией будущего релиза. Новую версию `>1.7.2` установить только по факту публикации, не угадывать. Не делать push/build/publish в рамках этой локальной задачи.
2. В управляемой политике `MobileAppReleasePolicy` после появления реальных версий выставить `minimumSupportedVersion.ios` и `.android` на опубликованные новые версии, а `storeUrl` — на официальные HTTPS магазины. Клиент `RequiredAppUpdateGate` уже показывает блокирующий экран «Нужно обновить приложение» и кнопку магазина; **на старых сборках при недоступном публичном config возможен fail-open экран**, поэтому теперь дополнительно сервер `/api/v1/chats/*` отдаёт **HTTP 426 `CHAT2_MOBILE_UPDATE_REQUIRED`** для `X-Client-Platform: ios|android` с отсутствующей/невалидной/слишком старой `X-Client-Version`. Если server minimum version отсутствует, мобильный Chat2 закрывается (`503`). Заголовки версии **не заменяют** настоящую auth/BAN ACL: spoofed header не даёт права читать чат.
3. Только после подтверждения публикации **обеих** платформ и публичного policy выставить GitHub production vars `CHAT2_MOBILE_STORES_VERIFIED=true`, `CHAT2_MOBILE_IOS_MIN_VERSION=<фактическая новая iOS>`, `CHAT2_MOBILE_ANDROID_MIN_VERSION=<фактическая новая Android>`. Они попадут и в API Compose env для `426`. Нельзя выставлять verified до реальной публикации.
4. Сгенерировать четыре новых **разных** server secrets, добавить в соответствующие защищённые GitHub Actions secrets; настроить приватную маршрутизацию. Release `--candidate` валидирует env/version/differing secrets **и обязательно читает реальный публичный Mobile config для обеих платформ** (GET, без записи) ещё до скачивания образов; `--release` повторяет эту проверку и дополнительно сверяет реальные приватные running services/WSS. Пропуск шага должен блокировать релиз, без silent downgrade.
5. Координированно опубликовать новое API + Web + broker конфигурацию + Mobile policy после проверки. Нельзя выкатывать старый broker с новой API-конфигурацией или новый broker с JWT fallback. В рабочем окружении мониторить 426/403/proxy 5xx, подтверждать Web+новые Mobile, **BAN существующей подписки → unsubscribe → повторный вход с ранее выданным JWT запрещён**, proxy outage → deny, восстановление подключений только после новой readGate.
6. При неисправности брокера **не возвращать старые room JWT**. Предпочесть временно отключить realtime и оставить авторизованные HTTP-операции с `readGate` (и `426` для старой Mobile), либо откатить только на такой уже проверенный безопасный выпуск, который также запрещает старый JWT. Cloud/production rollback отдельно согласуется.
