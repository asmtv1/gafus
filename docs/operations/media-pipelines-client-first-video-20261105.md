# GAFUS Media V2 — client-first фото, видео 720p и только Cloud.ru 360p

Дата: 05.11.2026. Эта документация описывает **локальную подготовку**, не выполненный production cutover. Мутации Cloud.ru, S3, Beget, VPS, production БД, магазинов, Git push и GitHub переменных в рамках подготовки **не выполнялись**. Старый проект `gafus1` не трогаем.

## Окончательная архитектура (уточнение 05.11.2026)

| Поверхность | Подготовка на устройстве / в браузере | Cloud.ru | S3 и состояние |
|---|---|---|---|
| **Моменты** | Фото WebP (миниатюры и финальные варианты); видео **MP4 720p + одна обложка WebP** | **Только необязательный MP4 360p**, без повторного 720p/постера | Клиент загружает готовые файлы; backend публикует проверенные 720p и клиентский постер; в фоне добавляется 360p. Перемещение/удаление/очистка — существующий GAFUS Worker, где есть соответствующий обработчик |
| **Чат 2.0** | Фото WebP, видео **MP4 720p + одна обложка WebP** | **Только необязательный MP4 360p**, без повторного 720p/постера | S3 подтверждение клиента, ACL, READY; операции очистки/удаления через существующий Worker |
| **Вопросы** | Фото WebP в нужных размерах | **Ничего** | **Цель:** Worker проверяет S3, сохраняет результат, выполняет очистку. В текущем коде завершение S3 HEAD/COPY и транзакция READY/QuestionPhoto ещё выполняются `apps/api/src/modules/questions/media-v2-upload.ts`; Worker запускает HMAC janitor, а удаление S3 делает API по этому запросу. Это оставшийся перенос, не объявляем его выполненным |
| **Фотоальбомы** | Готовые WebP thumb/full | **Ничего** | Worker выполняет durable S3 move/delete и janitor (`gallery-local-maintenance.ts`). **Цель:** проверку S3 полностью обслуживает Worker; сейчас синхронное подтверждение с HEAD и публикацией находится в `packages/core/src/services/gallery/service.ts` и исполняется из API |
| **Ветеринарные вложения** | Загрузка оригинала (пока отдельный контракт) | **Ничего** | Сервер синхронно создаёт превью при загрузке; никакого Cloud photo Job; устаревшие задания vetPreview закрываются, а S3 maintenance выполняет Worker |

**Одна обложка:** `poster.webp` создаётся клиентом и служит обеим версиям видео. Cloud.ru не должен читать, кодировать, записывать или заменять этот постер. Cloud.ru получает в качестве входа подтверждённый MP4 720p и публикует только `video/360.mp4`. Отказ или исчерпание повторов 360p не должен менять статус READY 720p.

**Разграничение API и Worker:** API сохраняет обязанности по JWT/owner/ACL, выдаче подписанных POST, фиксации конечного статуса и ответу клиенту. Буквальный перенос *всех* S3 HEAD/COPY/DELETE и сохранения результатов из API в Worker ещё требует изменения контрактов завершения и тестирования на реальной БД; синхронная выдача READY нельзя заменить на асинхронную без изменения UX/клиентов. Поэтому состояние по вопросам/галерее ниже — **частично перенесено**, несмотря на готовые janitor-пути.

**Важно:** Cloud.ru получает только **четыре активных видео-Jobs** `gafus-feed-video`, `gafus-feed-video-2`, `gafus-chat-video`, `gafus-chat-video-2`. Источники образов: `feed:worker:Dockerfile` и `chat:video:Dockerfile.chat2-job`. Gallery, Questions, Feed Photo, Chat Photo контейнеры больше не включены в declared release inventory и в job image publish matrix. Старые физические Cloud.ru Jobs, если ещё существуют в аккаунте, не удаляются автоматически: это отдельная управляемая инфраструктурная операция с предварительной проверкой отсутствия работы.

## Порядок production-перехода (НЕ выполнен)

1. Запустить полный source-only release контракт `node ci-cd/scripts/media-pipeline-guard.mjs` и `node --test ci-cd/scripts/media-pipeline-guard.test.mjs` плюс `pnpm test:cloudru-media`, `pnpm --filter @gafus/feed-cloud-runtime test`, тесты Core, Mobile/Web client photo/video; просмотреть отчёты `git diff --check`, TypeScript, YAML.
2. Подтвердить завершение публикации новой магазинной Mobile версии, содержащей клиентский WebP/MP4 compressor. Старая совместимость upload/job фото не поддерживается. До фактической публикации не включать принудительное обновление / Chat2 proxy-only.
3. По отдельному разрешению собрать и опубликовать **два** Cloud.ru образа в отдельном `cloudru-media-images.yml` с immutable digest, FFmpeg, проверенной 360p обработкой **без постера**. CI приложения **не строит** и **не пушит** Cloud.ru media images автоматически; только синхронизирует заранее проверенные immutable images. Убедиться, что образ, фактически привязанный к обеим Feed Jobs, содержит код 360p-only, иначе новая версия API и старый контейнер будут несовместимы.
4. По отдельному согласованному production release запустить read-only preflight **ровно четырёх** Jobs (two Feed and two Chat, в разных организациях Cloud.ru). Если есть дрейф образов/секретов или старые ожидаемые 11 Jobs — fail-closed; не включать `READY`/верификационные флаги только по плану.
5. Развернуть API/Web/Mobile backend и существующий Worker в согласованной версии; активировать и сверить видеопулы по подтверждённым image SHA и HMAC. Проверить S3 HEAD/GET/Range, Web/Mobile фото client READY, видео 720 READY **до** 360, добавление только 360p без повторного 720p и без нового постера, быстрые retries/зависания, удаление/отмену, `Gallery`/`Questions`/`Chat2` cleanup, признаки отсутствия фото-Cloud Job invokes.
6. Только после успешного E2E постепенно отключить/удалить устаревшие физические фото/галерея Jobs в Cloud.ru через отдельно подтверждённую инфраструктурную процедуру. Никакого массового удаления и автоматического re-creation. Подтвердить, что ненужные Cloud.ru фотообразы больше не публикуются.

## Особые правила безопасности и надёжности

- Не интерпретировать отсутствие 360p как ошибку публикации 720p; отсутствие 720p никогда не компенсировать опасным старым Cloud transcode.
- Каждый callback обязателен с актуальным `attemptToken`, статусом и lease; API независимо проверяет S3 metadata и immutable keys. Reconnect/retry не должен обходить ACL/BAN.
- Никогда не удалять готовые варианты по ошибке необязательного фона, не очищать оригинал до завершения окна повторного presigned POST.
- Не логировать presigned URL, S3 access keys, авторизационные токены. Ошибки фото должны быть видимы на конкретном вложении с повторным локальным кодированием, без бесконечного ожидания cloud queue.
- **Текущий production статус не подтверждён**: source-only PASS не означает, что запущенный Cloud.ru образ содержит новые кодеки или что четыре Jobs фактически синхронизированы.

## Релизные проверки

- `ci-cd/scripts/media-pipeline-guard.mjs`: запрещает восстановление photo image в публикации, устаревшие Cloud Job inventory, старые переменные Chat Photo / Questions Worker, серверное 720p **или постер** в Feed и Chat2 процессорах. Негативные контрактные тесты `ci-cd/scripts/media-pipeline-guard.test.mjs` запускаются из главного CI **и** вспомогательного workflow публикации образов.
- `infra/cloudru/production-job-release.mjs --plan`: read-only план четырёх видео-Jobs, **не** deploy.
- Для настоящих S3/CDN/E2E обязательна отдельная isolated QA, прежде чем объявлять релиз готовым. Ни пользовательские данные, ни production креденшелы не используются в локальных синтетических тестах.
