# @gafus/mailer

Транзакционные письма приложения: Resend HTTPS API или SMTP для локального relay / отката.

## Настройки

```env
MAIL_PROVIDER=resend
RESEND_API_KEY=<secret>
RESEND_FROM=notifications@notify.gafus.ru
MAIL_FROM_NAME=Гафус
MAIL_REPLY_TO=api@gafus.ru
RESEND_WEBHOOK_SECRET=<separate webhook signing secret>
```

Без MAIL_PROVIDER наличие RESEND_API_KEY выбирает Resend, иначе SMTP. Явное MAIL_PROVIDER=resend без ключа завершается ошибкой, без скрытого переключения на SMTP. RESEND_FROM отделён от старого MAIL_FROM, чтобы не отправлять с неподтверждённого адреса Яндекса. Ответы направляются в MAIL_REPLY_TO.

Для SMTP: MAIL_PROVIDER=smtp и SMTP_HOST, SMTP_PORT, SMTP_SECURE, SMTP_USER, SMTP_PASS, MAIL_FROM. Настройки Телемоста независимы от транспорта почты.

## Журнал

Перед отправкой Resend создаётся TransactionalMailAttempt. ACCEPTED означает приём провайдером, а не доставку. Сохраняются ID провайдера, число получателей, время и код ошибки; содержимое письма и токены сброса пароля не сохраняются. UNKNOWN означает, что сеть оборвалась и результат приёма неизвестен.

Для консультаций deliveryKey равен consultation-<ConsultationEmailLog.id>. Повторы используют тот же Idempotency-Key; уже принятые письма не отправляются заново. При неопределённом результате старше 23 часов требуется ручная сверка, поскольку Resend хранит ключи идемпотентности 24 часа. Остальные вызывающие стороны без deliveryKey создают отдельные попытки для каждого вызова.

POST https://gafus.ru/api/webhooks/resend проверяет подпись Svix по исходному телу, затем сохраняет TransactionalMailEvent. Уникальный ID события защищает от дублей; история сохраняется отдельно от попыток, поэтому порядок прихода событий не затирает информацию. Bounce type/subType сохраняются в errorCode, подробная диагностика доступна в Resend по providerMessageId. Неверная подпись — 400, отсутствие секрета или ошибка БД — 503 для повторной доставки.

## Ввод в эксплуатацию

1. Подтвердить notify.gafus.ru в Resend.
2. Добавить RESEND_API_KEY в корневой локальный .env и GitHub Secrets.
3. Создать webhook с URL https://gafus.ru/api/webhooks/resend; выбрать email.sent, email.delivered, email.delivery_delayed, email.bounced, email.failed, email.complained, email.suppressed. Signing secret сохранить как RESEND_WEBHOOK_SECRET в локальном .env и GitHub Secrets.
4. Применить миграцию 20261011173000_resend_mail_journal до запуска нового приложения. CI/CD передаёт ключи web, API и worker; без миграции отправка завершится ошибкой до обращения к провайдеру.
5. Проверить тестовые отправки на Яндекс/Mail.ru/Gmail, события в журнале и реальный сценарий консультации.
6. Проверять суточный лимит Resend Free (100) отдельно от месячного (3000). Автоматического переноса писем при 429 в этом пакете нет: ошибки передаются вызывающей стороне / очереди.

Локальные команды: pnpm --filter @gafus/mailer build; pnpm --filter @gafus/mailer test.

Вложения: Buffer, строка с encoding, локальный путь; cid сохраняется. Потоки и удалённые пути отклоняются до отправки.

## Повторные отправки и расследование сбоев

- Resend делает до **3 попыток внутри одного вызова** с задержками 400 и 1200 мс при сетевой ошибке, HTTP 5xx или невалидном HTTP 2xx. Во всех запросах **одинаковые** тело и Idempotency-Key. Для каждой попытки fetch действует таймаут 20 секунд. HTTP 429, 401/403 и прочие 4xx повторно автоматически не отправляются.
- В TransactionalMailAttempt.errorCode сохраняются только безопасные идентификаторы (NETWORK_ETIMEDOUT, NETWORK_EAI_AGAIN, NETWORK_OTHER, HTTP_503, INVALID_PROVIDER_RESPONSE и т.п.). Текст исключения, адреса и токены **не сохраняются**. ACCEPTED подтверждает только приём Resend; email.delivered подтверждается webhook.
- После **23 часов** с создания попытки при неопределённом исходе автоматическая повторная отправка с прежним deliveryKey запрещена: нужна сверка с Resend и актуальности письма (ключ идемпотентности хранится там лишь 24 часа).
- Обработчик раз в 15 минут (UTC, минуты 3/18/33/48) выводит агрегированный Transactional mail requires attention в логи worker, если есть зависшие PENDING старше 5 минут, UNKNOWN старше 5 минут, UNKNOWN старше 23 часов, FAILED за сутки или email.failed/email.bounced/email.complained/email.suppressed за сутки. Пользовательские данные в предупреждения не включаются.
- GET http://worker:3003/metrics/mail экспортирует gafus_mail_stalled_pending, gafus_mail_unresolved_unknown, gafus_mail_expired_unknown, gafus_mail_recent_failed, gafus_mail_delivery_failures_24h. Alloy собирает их каждые 60 секунд и после выкладки конфигурации отправляет в Yandex Monitoring (алерты нужно настроить в Yandex Monitoring отдельно, порог > 0 минимум 5 минут).
- При UNKNOWN **нельзя утверждать, что письмо не ушло**, пока не проверены история и события Resend. Журнал не хранит текст письма и секретные ссылки: произвольно восстановить письма из одной записи невозможно. Для консультаций можно реконструировать письмо через ConsultationEmailLog, но перед ручным повтором необходимо проверить актуальность бронирования и неистёкший 23-часовой срок. Нельзя запускать массовый resend вслепую.
- Для контрольной отправки на delivered@resend.dev используйте отдельный стабильный deliveryKey и проверяйте ACCEPTED, email.sent, email.delivered по providerMessageId. Тестовый адрес не является личным почтовым ящиком получателя.

## Durable outbox Resend (опциональный ввод в эксплуатацию)

Новые письма после включения ставятся в долговечную таблицу TransactionalMailOutbox
и обрабатываются серверным worker каждые 60 секунд. Письма зашифрованы
AES-256-GCM (отдельный случайный nonce и authentication tag на сообщение,
ID письма — AAD); plaintext адресов, вложений, ссылок и кодов в таблице нет.
После ACCEPTED / FAILED / EXPIRED зашифрованный payload стирается.
Повторная постановка с прежним deliveryKey не перезаписывает исходное
содержимое и не обходит статус отправки.

В production по умолчанию MAIL_OUTBOX_ENABLED=false. Для включения:
1. Сначала применить миграцию 20261014160000_transactional_mail_outbox.
2. Сгенерировать отдельный случайный 32-байтный ключ в виде 64 hex символов;
   сохранить в GitHub Secret MAIL_OUTBOX_ENCRYPTION_KEY. Не использовать
   RESEND_API_KEY/JWT_SECRET вместо него, не логировать и не отправлять
   ключ по почте. Сохранить ключ в защищённом резервном хранилище:
   его потеря делает ещё неотправленные письма нечитаемыми.
3. Добавить GitHub variable MAIL_OUTBOX_ENABLED=true. Workflow передаст
   переменные в web/api/worker через docker-compose.prod.yml.
4. Проверить /metrics/mail, вкладку админки «Почта и алерты»
   и тестовое письмо delivered@resend.dev. Убедиться, что старые
   проблемные попытки не воспроизводятся автоматически.

Повтор после сбоя Resend выполняется по атомарному lease в PostgreSQL:
не более 30 сообщений за проход (по умолчанию 10), отсрочки
1/5/15/30/60 минут, один Resend Idempotency-Key на письмо,
не более 20 часов от первого добавления и меньше индивидуального TTL.
Ошибки 401/403, неверные адреса и неподдерживаемые вложения требуют
операторской проверки, квоты 429 повторяются с отложенным запуском.
Истёкшие письма не отправляются.

Для security-сценариев с короткоживущими или заменяемыми токенами
(сброс пароля, подтверждение нового email, одноразовый код удаления аккаунта)
выбрана IMMEDIATE-отправка: до трёх сетевых попыток в одном запросе,
без долговременного хранения URL/кода в очереди. Повтор такого сценария
должен создавать *новый* токен через пользователя.

Для консультаций используется существующий consultation-email-log ID,
для чеков NPD — стабильный ID доставки, для уведомлений о продлении —
ID подписки + период. Напоминания о скором старте консультации
имеют TTL 10 минут, уведомления о списании в ближайшее время — 45 минут,
другие письма ограничены отдельными короткими TTL.

Мониторинг: администратор видит отдельную вкладку «Почта и алерты»
и индикатор в десктопном/мобильном меню. Данные обновляются раз в
30 секунд при открытой вкладке; показываются только коды ошибок,
время и технические короткие ID, без PII. Это не внешний push:
алерты отображаются в админке, а Prometheus отдаёт счётчики
для дальнейшего включения внешних уведомлений.
