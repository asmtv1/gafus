# Опросы в «Моментах» — чек-лист релиза

**Локально подготовлено, в production ещё не выпускалось.** Опросы — встроенная часть Feed:
никакого отдельного флага включения нет. Если раздел «Моменты» работает,
после релиза будут доступны создание, просмотр и голосование в опросах.

**Важно:** push в `main` автоматически запускает production-деплой и Prisma-миграции.
Не выполнять push, миграцию production или деплой без отдельного разрешения.

## До push / деплоя

1. Проверить Git-корень `/Users/asmtv1/Desktop/gafus1`, ветку `main` и
   незакоммиченные изменения. Не перезаписывать параллельную работу (особенно CDN).
2. Убедиться, что в релиз включена **аддитивная** миграция
   `packages/prisma/migrations/20261014000000_feed_polls/migration.sql`,
   а также Web, API, Worker и пакеты Prisma/Core/Types/Feed Server. Схема БД
   **обязана** быть мигрирована до обработки новой версии приложения.
3. CI должен успешно пройти: проверка SQL миграции на выделенной временной
   PostgreSQL, интеграционные тесты Feed API и очереди публикаций,
   UI-тесты Web/Mobile, проверка отсутствия отдельного флага опросов.
   Запускаемые локально проверки:
   `node --test ci-cd/scripts/feed-poll-release-contract.test.mjs`,
   `python3 packages/prisma/scripts/generate-fresh-db-extras.py --check`.
4. Проверить TypeScript/ESLint, успешные сборки Core, Feed Server, Web и
   совместимость Mobile. Реальный staging-сервер в проекте отсутствует.
5. Получить разрешение на релиз. **Нет промежуточного этапа, на котором
   миграция опубликована, но опросы скрыты флагом.**

## Авторизованный выпуск

1. По штатному production workflow проверить резервную копию и успешное
   применение миграции. Если migration job падает — **не запускать** новую
   версию приложения до устранения причины; не править production-БД вручную.
2. Проверить развертывание согласованных версий Web, API и Worker; существующие
   `FEED_ENABLED`/`FEED_PROCESSOR_READY` остаются общими требованиями раздела.
   Опросы **не требуют** дополнительных переменных окружения или рестартов
   ради включения функции.
3. Проверить авторизованный `/api/v1/feed/status` (`enabled: true`), а затем
   UI создания/просмотра опроса в Web и выпущенном Mobile. Старый Mobile без
   виджета опроса увидит текст «Опрос» вместо пустой карточки.
4. При отдельном разрешении создать контрольную публикацию: вопрос с несколькими
   ответами и фотографией варианта, дождаться обработки файла, проголосовать
   с другого аккаунта, убедиться в корректном скрытии результатов/ответов и
   запрете двойного голосования; проверить удаление и постановку файла на очистку.
5. Проверять 4xx/5xx Feed, очереди обработки, S3/CDN, подписанные URL,
   производительность опросов и нагрузку на PostgreSQL. Не менять CDN origin
   или production-хранилище ради опросов.

## Если после релиза обнаружена проблема

1. **Отдельного выключателя опросов нет по решению владельца продукта.**
   Не пытаться использовать удалённый флаг. Остановить распространение нового
   релиза и согласовать откат образов / точечный hotfix через стандартный workflow.
2. Сохранить таблицы `FeedPoll*`, варианты ответов и голоса. Миграция
   аддитивная, **откат схемы/удаление голосов не является безопасным**.
3. Перед откатом образов проверить совместимость старого Feed API с новой
   схемой и опубликованными poll-only постами. У более старого релиза может не
   быть поддержки опросов, поэтому визуально и функционально откат не равен
   отключению отдельного флага.
4. Не уничтожать незавершённые публикации и задания загрузки файлов; оценить
   их состояние и повторять их только после проверки idempotency/lease.
5. Восстановить нормальную работу через проверенную новую версию либо
   согласованный hotfix, с сохранением данных проголосовавших пользователей.

- Нативный Mobile release в магазинах и тесты на физических устройствах.
- Контрольная production-публикация и проверка метрик после разрешённого релиза.
