# Чистая прибыль — контракт первой версии

Раздел `/main-panel/profit`, только ADMIN. История начинается 01.09.2026,
календарные даты — Europe/Samara (UTC+4). Входящий налог здесь расчётный,
не фактическое начисление ФНС. Чеки НПД и условия подписок не изменяются.

## Источники и формула

Все суммы вычисляются в целых копейках. НПД округляется до копейки по операции.

`Оплаты − возвраты − удержания ЮKassa − НПД − начисления партнёрам − видео − сервер`.

- Только успешные подписочные платежи YOOKASSA (включая впоследствии возвращённые).
  Дата дохода — `providerCapturedAt`; `succeededAt` служит предварительной датой
  для несверенной истории. Не использовать дату создания попытки оплаты.
- Удержание: `amount − providerIncomeAmount`, уже с НДС с комиссии.
  Проценты публичных тарифов не подставляются. Источник типа оплаты — provider API.
- Возврат учитывается один раз по ID ЮKassa, в дату `created_at` подтверждённого
  возврата. Исходная выручка остаётся в своём месяце, комиссия не удаляется.
  В дату возврата расчётный НПД уменьшается на 4% возвращённой суммы.
- `PartnerCommission.amountKopecks` со знаком, по дате начисления. Используются
  только начисления по платежам, входящим в историю этого раздела.
  `PartnerPayout` повторно не вычитается. Правила начисления/коррекции сохраняются.
- Видео: `quantity × 50000`, по введённой дате выплаты. Цена фиксируется в записи;
  создание идемпотентно, редактирование проверяет версию, отмена сохраняет историю.
- Сервер: 42900 копеек 18-го числа каждого прошедшего месяца с сентября 2026.
  Это регулярное обязательство, а не доказательство банковского списания.

Расчёт читается в транзакции RepeatableRead. Сводка обходит платежи порциями по
500, таблицы имеют страницы по 25. Открытие раздела не обращается к ЮKassa.

## Полнота

Без точной даты, суммы удержания либо сверенной истории возвратов итог `null`.
Экран показывает известные составляющие и сообщение о необходимости сверки.
Недатированная успешная история блокирует окончательный результат до сверки.
Непроверенные возвраты более ранних включённых оплат блокируют и последующие
периоды: возврат мог произойти в выбранном месяце.

У старых платежей `financeRefundsIncomplete = true`. Новая подтверждённая оплата
в webhook/worker начинает историю без возвратов. Сбой записи возврата помечает
историю неполной, сохраняя существующее поведение доступа и чеков.

## Интерфейс

PageLayout, MUI, существующие меню и оформление админки. Период → результат →
разбивка → история оплат видео → детализация оплат подписок. Новая тема,
дизайн-система и зависимости для оформления не добавляются.

## Выпуск

1. Сохранить резервную копию целевой БД и зафиксировать версии приложений.
2. Применить добавочную миграцию `20261005190000_profit_finance` штатным
   `prisma migrate deploy`; не использовать `db push` на production.
3. Обновить Prisma client/core и платёжные потребители: API/web для webhook,
   worker для автопродлений, админку. Установить штатные переменные окружения.
4. Из корня проекта запустить проверку истории:

   ```sh
   pnpm --filter @gafus/worker profit:sync --dry-run
   ```

   Требуются DATABASE_URL и YOOKASSA_SHOP_ID/YOOKASSA_SECRET_KEY в штатном
   окружении (`profit:sync` читает корневой `.env`). Команда делает только GET
   запросы к провайдеру; dry-run не изменяет БД. Логи не содержат ключей.
5. После успешной проверки выполнить локальное заполнение:

   ```sh
   pnpm --filter @gafus/worker profit:sync --apply
   ```

   Команда не меняет статусы, доступ, тарифы, начисления и чеки. Историю возвратов
   помечает сверенной только после полной пагинации и при отсутствии параллельного
   изменения платежа. Повторный запуск не дублирует возвраты.
   Код выхода 2 означает неполные платежи/конкурентные изменения; 1 — сбой команды.
6. Сверить сентябрь и текущий месяц с ЮKassa и партнёрским журналом. Проверить
   новую оплату, автопродление, возврат и ручной расход под ADMIN. Проверить отказ
   для MODERATOR и других ролей. Доступ к странице не означает полноту данных:
   до завершения сверки результат должен оставаться неполным.

При откате вернуть предыдущие приложения, сохранив новые таблицы и столбцы.
Не удалять финансовые записи и историю правок. Пуш и production-выпуск требуют
отдельной команды пользователя.

## Изолированная проверка

Интеграционный тест требует выделенную PostgreSQL-базу с именем
`gafus_profit_qa...` и флаг `PROFIT_INTEGRATION_TESTS=1`. Тест удаляет только свои
фикстуры с префиксом `profit-test-` в этой выделенной БД; на обычной БД пропускается.
Для подготовки новой тестовой БД применить schema/migrations отдельно от production.

## Результаты локальной проверки (05.10.2026)

- 129 целевых тестов: 101 core (расчёт, разбор данных, сверка, webhook,
  партнёрский журнал и чеки), 7 интеграционных на выделенной PostgreSQL,
  15 worker, 6 серверных действий админки.
- Prisma validate / generate, typecheck core / worker / admin-panel,
  ESLint новых модулей и изменённой навигации, сборки core и admin-panel,
  `git diff --check`.
- Добавочная миграция применена к отдельной БД со старой схемой и существующим
  платежом. Старый платёж сохранил статус и сумму; новые финансовые поля
  остались незаполненными, история возвратов отмечена несверенной.
- Браузер: ширины 1440 / 768 / 390, прибыль, убыток, пустой период,
  неполные комиссии; создание / изменение / отмена видео, длинное имя и
  комментарий, desktop и мобильная навигация, отказ для MODERATOR.
  На 390 px ширина документа равна ширине viewport; прокрутка только в таблицах.
  Соседние разделы подписок и партнёров открываются.
- В существующем файле worker автопродлений ESLint сообщает 21 ошибку
  `no-explicit-any` и одно предупреждение. Сравнение с HEAD подтвердило
  идентичный набор сообщений; новых ошибок не добавлено. Новые модули,
  тесты и UI проходят ESLint. Сборка также сохраняет прежнее предупреждение
  BullMQ о динамической зависимости в разделе консультаций.
- На локальных фикстурах отсутствует файл аватара `/uploads/avatar.svg` (404);
  эта ошибка ресурса также присутствует на соседних страницах.

Это локальные доказательства на тестовых данных. Production-миграция,
историческая сверка реальных платежей и проверка после выпуска не выполнялись.
