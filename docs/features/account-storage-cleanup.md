# Удаление аккаунта и файлов

Самостоятельное удаление и удаление через админку вызывают одну транзакционную подготовку очистки. До `User DELETE` сохраняются независимые от пользователя задачи `AccountStorageCleanup`, а также существующие задачи галереи и ленты. Ошибка записи задач откатывает удаление профиля.

## Что удаляется

- БД: пользователь, профиль, питомцы, документы, посещения врача и вложения, вопросы с ответами и фотографиями, альбомы, посты с медиа и связанные записи по каскадам Prisma.
- Публичный бакет: аватар, фото/документы питомцев, фото вопросов, видеоотчёты экзаменов. Снимок включает фото чужих ответов на вопросы удаляемого пользователя. Папки пользователя и экзаменационных шагов проверяются целиком, включая файлы без актуальной ссылки в БД.
- Приватная галерея: `albums/{ownerId}/` и `users/{ownerId}/`, включая оригиналы и превью посещений врача, временные и незавершённые загрузки.
- Приватная лента: `posts/{ownerId}/`, включая изображения, видео, плейлисты, сегменты и незавершённые загрузки.
- Stream: зарегистрированные вложения пользователя в сообществе и все вложения удаляемого личного диалога. Канал, тип файла и URL сохраняются до каскада; вызывается официальный `deleteImage`/`deleteFile`, после чего прежняя CDN-ссылка проверяется запросом HEAD. Подтверждением служат только 404/410. Успешное удаление у провайдера с ещё доступным CDN-файлом, 403 из-за истёкшей подписи и сетевые ошибки оставляют задачу на повтор и требуют диагностики при длительном ожидании.
- S3: удаляются также старые версии объектов и delete markers. Ошибки отдельных объектов в пакетном ответе запрещают завершение задачи.

Чужие ответы на комментарии удаляемого пользователя сохраняются: ссылки `rootId` и `replyToId` обнуляются. Чужие ответы на удаляемый вопрос удаляются вместе с вопросом.

## Повторы и CDN

`worker` проверяет очередь раз в минуту. Задачи имеют временную аренду и уникальный токен попытки; параллельные реплики используют `FOR UPDATE SKIP LOCKED`. Нет лимита попыток, после которого задача теряется. Ошибки конфигурации/доступа оставляют её в `pending` с безопасным кодом ошибки; содержимое ошибок провайдеров и URL в лог не попадает.

Первая очистка выполняется после окончания выданных разрешений загрузки, аренды обработчиков и резервов вложений врача плюс 10 минут. Загрузки публичных пользовательских файлов и Stream сериализованы с удалением профиля и ограничены по времени.

После удаления объектов создаются адресные purge-запросы во **все настроенные CDN-ресурсы** соответствующего хранилища. Операции сохраняются после каждого запроса: большой аккаунт продолжает очистку с последнего подтверждённого запроса. После минимум 15 минут выполняются повторная проверка объектов и проверка статуса операции CDN. Если найдены поздние файлы, удаление и purge повторяются. `done` означает подтверждение очистки объектов и операций CDN, а не только принятие purge-запроса. Идентификаторы пользователя сохраняются для диагностики; URL удаляются из завершённой задачи.

Публичный Nginx не читает и не записывает кэш для `/uploads/users/`, `/uploads/questions/`, `/uploads/exams/`; ответы имеют `private, no-store`. Кэш учебного контента сохраняется. При пересоздании Nginx старый каталог proxy cache очищается до запуска, поэтому старые кэшированные пользовательские файлы физически не сохраняются на сервере. Ранее скачанные файлы и уже сохранённый браузерный кэш на чужих устройствах сервер удалить не может.

Stream удаляется через API провайдера; внутреннее устройство и сроки его CDN-кэшей не управляются нашим Yandex purge. Проверка реальных CDN обязательна перед заявлением о production-готовности.

## Включение при развёртывании

1. Применить миграции, включая `20261010160000_account_storage_cleanup`. Предшествующая миграция посещений врача также обязательна. Пересобрать пакеты и приложения.
2. Выдать worker доступ к публичному бакету и обоим приватным бакетам: list objects/versions и delete objects/versions. Используются `YC_ACCESS_KEY_ID`, `YC_SECRET_ACCESS_KEY`, `GALLERY_BUCKET`, `GALLERY_S3_ACCESS_KEY_ID`, `GALLERY_S3_SECRET_ACCESS_KEY`, `FEED_BUCKET`, `FEED_S3_ACCESS_KEY_ID`, `FEED_S3_SECRET_ACCESS_KEY`. Значения бакетов должны совпадать с приложениями и обработчиками загрузок.
3. Передать worker `CDN_CLEANUP_SERVICE_ACCOUNT_KEY`: JSON авторизованного ключа сервисного аккаунта с правом очищать соответствующие CDN-ресурсы и читать операции. Worker самостоятельно получает и обновляет IAM token. Не использовать короткоживущий статический IAM token. Это серверный секрет, не клиентская переменная.
4. Указать `GALLERY_CDN_RESOURCE_IDS` и `FEED_CDN_RESOURCE_IDS` — все ID CDN-ресурсов/алиасов через запятую. При общем CDN один ID указывается в обоих списках. Terraform выводит `cdn_resource_id`. Без этих значений приватные задачи не завершаются. Если перед публичным бакетом есть дополнительный Yandex CDN, перечислить его ресурсы в `PUBLIC_CDN_RESOURCE_IDS`; иначе публичные URL обслуживаются Object Storage и Nginx без пользовательского кэша.
5. Передать `STREAM_API_KEY`, `STREAM_API_SECRET`, если есть вложения Stream. Очистка не зависит от публичных флагов доступности чатов.
6. Включить `ACCOUNT_STORAGE_CLEANUP_ENABLED=true` после миграции и настройки. Флаги `GALLERY_ENABLED`/`FEED_ENABLED` не отключают эту очередь.
7. Пересоздать Nginx с обновлёнными конфигурацией и командой запуска. Простого reload недостаточно для физического удаления прежних cache-файлов.

Самостоятельное удаление уже существовавших профилей до этой миграции могло потерять ссылки на файлы. Новая очередь не восстанавливает потерянные ссылки автоматически. Очистка исторических сирот — отдельная сверка объектов с БД/аудитом; она не должна удалять файлы действующих пользователей по догадке.

## Проверка

- Unit: сервисы удаления профиля/админки, очередь, S3-адаптер, IAM/purge-запросы и контроль результата, загрузки чата и экзамена.
- PostgreSQL: `ACCOUNT_CLEANUP_TEST_DATABASE_URL` указывает только на временную локальную БД с пользователем `cleanup_test` на `127.0.0.1:55439`. Запуск: `pnpm --filter @gafus/core exec vitest run --config src/services/accountCleanup/vitest.config.ts`. В схеме должны быть применены миграции. Тесты проверяют реальный каскад, сохранение очереди, откат, аренду, повторы и завершение после CDN.
- Production smoke после развёртывания: отдельный тестовый аккаунт со всеми типами медиа; прогреть ссылки в каждом CDN; удалить профиль; дождаться `done` всех задач; проверить отсутствие объектов/версий и недоступность **прежних прогретых URL**. Повторить удаление через админку и сценарий временного отказа S3/CDN. Для Stream отдельно проверить старые ссылки.

Без production smoke локальные проверки не подтверждают права сервисных аккаунтов, полноту списка CDN-ресурсов и фактическое удаление из развёрнутых хранилищ.
