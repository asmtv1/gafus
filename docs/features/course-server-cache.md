# Серверный кэш уроков GAFUS Main

## Этап 2 — реализация (по умолчанию выключена)

Общая для Hono API и Next.js Web точка чтения в
`packages/core/src/services/training/trainingService.ts` вызывает
`getTrainingDayContent` из `trainingDayContent.ts`.

В кэш попадают только общие данные DayOnCourse, TrainingDay, Step, Course:
текст, структура и метаданные. В кэш **не входят** права доступа,
персонализация, пользовательские статусы, таймеры, прогресс и результаты
проверки платных/приватных/монетизированных шагов. Они вычисляются заново для
каждого запроса. URL, JSON Web/Mobile и офлайн-форматы не изменяются.

| Параметр | Значение |
| --- | --- |
| Флаг | `ENABLE_COURSE_CACHE=true` |
| По умолчанию | **выключен** |
| TTL | 60 секунд от момента записи |
| Лимит | 256 записей на Node.js процесс (LRU) |
| Ключ | `[courseType, dayOnCourseId]` |
| Cold-miss | одновременные запросы одного ключа объединяются |
| Ошибка кэша | непосредственный запрос Prisma |
| Ошибка БД | передаётся существующему обработчику |
| Пустой результат | не сохраняется |

Предусмотрены локальные функции `invalidateTrainingDayContentCache`,
`invalidateCourseContentCache`, `clearTrainingDayContentCache`. Сброс защищает
от повторной записи старого результата выполнявшегося запроса.
Выключение флага при следующем чтении сбрасывает кэш, но для изменения env
в production обычно требуется перезапуск процесса.

## Этап 3 — локальная автоматическая инвалидация

Подключён сброс in-memory кэша после успешных записей в БД:

- trainerCourse.updateCourse и trainerCourse.deleteCourse: по ID курса
  (включая изменение порядка и связей дней);
- trainingDay.updateTrainingDay и trainingDay.deleteDays: по TrainingDay ID
  во всех курсах, которые используют общий день;
- trainerStep.updateStep, trainerStep.deleteSteps и removeStepImageUrl:
  по Step ID во всех днях и курсах, использующих общий шаг;
- trainerVideo.deleteTrainerVideoRecord: по ID шагов после успешного
  удаления ссылок на видео (даже если последующее удаление видео не удалось);
- dailyCourse.cleanupDailyCourseContent: по удалённым Step ID
  после успешной транзакции.

При ошибке записи или откате транзакции инвалидация не выполняется.
Прогресс UserTraining, UserStep, UserCourse, статусы и таймеры
не участвуют в общем кэше и не инициируют его сброс.

## Этап 4 — межпроцессная синхронизация через существующий Redis

> Исторический этап. Актуальная реализация и повторные замеры описаны в **этапе 8**.


Используем **уже существующий Redis** из docker-compose без новых
контейнеров или провайдеров. Для строгой консистентности добавлена
отдельная PostgreSQL-миграция (см. этап 6).

- Все успешные изменения курса, дня, общего шага или его медиа
  увеличивают глобальную версию по ключу
  `gafus:training-content:revision:v1` (атомарный Redis INCR).
- Перед **каждым** обращением к локальному кэшу Hono API и Web
  проверяют **две** версии: Redis GET и транзакционную версию
  PostgreSQL. Даже если Redis INCR потерялся после коммита, версия
  PostgreSQL меняется, и новый запрос очищает устаревший локальный кэш.
- Если Redis недоступен, истёк тайм-аут 800 мс или значение версии
  недостоверно, запрос **обходит** кэш и читает непосредственно Prisma.
  При восстановлении соединения кэш проверит версию и снова наполнится.
- Параллельные проверки версии с завершением в обратном порядке
  не могут возвратить процесс к более старой версии.
- Сигнал обновления не содержит пользовательских данных. Ключ
  общий для всех курсов: запись любого курса сбрасывает все
  локальные записи при следующем чтении. Точечная локальная
  инвалидация сохраняется как дополнительный механизм.

### Два rollout-флага (все по умолчанию false)

| Переменная | Где включить | Назначение |
| --- | --- | --- |
| `COURSE_CACHE_SYNC_ENABLED=true` | **Trainer Panel, Hono API и Web** | Участие в глобальной синхронизации Redis; у тренера публикует изменения |
| `ENABLE_COURSE_CACHE=true` | Hono API и Web (Trainer Panel не требуется) | Кэшировать тексты только если sync включён и Redis доступен |
| `REDIS_URL` | Все перечисленные сервисы | Существующее соединение Redis, без localhost fallback для кэша |

В `ci-cd/docker/docker-compose.prod.yml` обе переменные
передаются явно с `:-false`, то есть даже обновление образов
само по себе кэширование **не включает**.

Для безопасного поэтапного включения: сначала задать sync=true **во всех**
сервисах и проверить успешные обновления Redis после тренерских правок.
Только затем включать cache=true на читателях, предварительно протестировав
сценарии доступа и офлайн на staging.

### Ограничения и гарантии

- Redis GET **и лёгкий PostgreSQL SELECT версии** выполняются перед
  каждым использованием кэша. Это дополнительный запрос к PostgreSQL,
  поэтому нужен замер эффекта на staging.
- Версия в PostgreSQL увеличивается триггером **в той же транзакции**,
  что и курс, день, шаг или связь. Ошибка Redis INCR после коммита не
  приводит к 60-секундному устареванию на последующих запросах.
  Незавершённые запросы, начавшиеся до коммита, могут получить старый
  снимок — обычная гонка между чтением и записью.
- При Redis outage на чтении устаревший кэш не используется. При ошибке
  публикации после завершённой записи результат тренерского действия
  не превращается в ложную ошибку сохранения.
- Инвалидация существующих Next.js каталогов/страниц с `revalidateTag`
  остаётся самостоятельным механизмом; Redis версия защищает **только**
  новый in-memory кэш общей проекции тренировочного дня.

**Не включать в production до:** применения миграции до включения кэша,
staging-проверки платных/приватных курсов, офлайн и синхронизации прогресса,
проверки отказа Redis, p95 latency и процедуры отката.
Транзакционная инвалидация PostgreSQL уже реализована.

Добавлена только PostgreSQL-миграция версии/триггеров, без новых сервисов.
CDN для JSON не включён.


## Этап 5 — метрики, staging и откат

Метрики `trainingContentMetrics.ts` содержат только агрегированные
счётчики и длительность запросов, без пользователей, идентификаторов,
текстов или адресов медиа. В каждом Node.js процессе свои показатели;
они **сбрасываются при его перезапуске**.

| Показатель | Значение |
| --- | --- |
| `hit`, `miss`, `inflightReuse` | Попадания, промахи и объединённые запросы |
| `bypassDisabled`, `bypassRedis`, `bypassOverflow` | Причины обхода кэша |
| `revisionFlush`, `localInvalidation` | Сбросы по Redis и после изменений |
| `ttlExpired`, `eviction` | Истечение TTL и ограничение памяти |
| `redisReadFailure`, `redisPublishFailure`, `redisPublishSuccess` | Состояние синхронизации |
| `dbError`, `dbRevisionFailure`, `prismaRead` | Ошибки Prisma, проверки версии PostgreSQL и время чтения |

### Защищённые диагностические маршруты

- Hono API: `GET /metrics/course-cache`
- Next.js Web: `GET /api/internal/course-cache-metrics`

Оба принимают только `Authorization: Bearer <token>`. Переменная
`COURSE_CACHE_METRICS_TOKEN` должна быть **не короче 24 символов**.
Без токена или с неправильным — `404`; при успешном запросе
возвращается JSON со счётчиками и заголовком `Cache-Control: no-store`.
В docker-compose переменная передаётся в Web и API и **пустая по умолчанию**.
Токен хранить только на сервере; никогда не добавлять в
`NEXT_PUBLIC_*` или в мобильное приложение.

**Prometheus/Grafana-агрегация и алерты пока не подключены.**
Диагностические маршруты позволяют вручную сравнивать Web и API при
локальном/staging тестировании, без изменения текущей инфраструктуры
мониторинга и её незакоммиченных настроек.

### Проверки без реального staging

Unit-тесты проверяют изоляцию прав и персонализации, ошибки Redis,
инвалидацию после успешных записей и отсутствие событий при ошибке,
параллельные чтения, TTL, безопасность токена и статистику.
Дополнительный интеграционный тест моделирует два независимых
Node.js-модуля чтения, разделяющих одну имитацию Redis: оба читают
новую версию после изменения и обходят кэш при отказе Redis.

**Это не проверка живого Redis/PostgreSQL или staging/production.**

### Последовательность включения на изолированном staging

1. Развернуть staging с тестовыми данными и **применить миграцию
   `20261015020000_course_content_revision` до включения кэша**. Не
   переключать production и не затрагивать production-базу.
2. При `ENABLE_COURSE_CACHE=false` включить
   `COURSE_CACHE_SYNC_ENABLED=true` во **всех** процессах Trainer Panel,
   Web и Hono API. Подтвердить успешный Redis INCR при редактировании
   тестового курса, дня, шага и его видео.
3. Настроить отдельный длинный `COURSE_CACHE_METRICS_TOKEN` в Web и API;
   проверить `404` без него и наличие JSON после авторизации.
4. Включить `ENABLE_COURSE_CACHE=true` **только на Web и API**.
   Проверить, что при обновлении тренером в обоих читателях новое
   содержимое отображается без ожидания 60-секундного TTL.
5. Проверить анонимный просмотр, платные и приватные курсы, изменение
   разрешений, монетизированные шаги, двух разных пользователей, шаблоны
   персонализации, офлайн Mobile и синхронизацию прогресса после сети.
6. На staging отключить Redis: запросы должны продолжить работу напрямую
   через Prisma, `bypassRedis` вырасти; после восстановления Redis
   данные должны быть актуальны. Сравнить hit/miss, p95 latency и ошибки
   до/после. Решение о включении принимать только по реальным замерам.

### Откат флагом (без отката схемы)

Выставить `ENABLE_COURSE_CACHE=false` в Web и API, перезапустить
процессы, убедиться по диагностике в росте `bypassDisabled` и
успешном прямом чтении Prisma. `COURSE_CACHE_SYNC_ENABLED=true`
оставить до завершения перевода **всех** читателей на uncached режим.
Для отката кэша миграцию откатывать не требуется, как и менять DNS или CDN.

### Известное ограничение

Между уже начатым чтением и коммитом другого запроса существует
естественная гонка: ответ, начатый до коммита, может содержать старый
снимок. **Запросы после коммита**, успешно проверившие версию в
PostgreSQL, не используют старый локальный кэш, даже при потере Redis INCR.
При недоступной PostgreSQL-версии кэш обходится, а не считается актуальным.

## Этап 6 — транзакционная инвалидация PostgreSQL (исправление)

> Исторический этап. Актуальная реализация и повторные замеры описаны в **этапе 8**.


**Причина дефекта:** Redis INCR находился после коммита PostgreSQL. При
неудачной публикации остальные процессы не могли узнать, что курс
изменился, и ждали TTL до 60 секунд.

**Решение:** миграция `packages/prisma/migrations/20261015020000_course_content_revision/migration.sql`
создаёт одну строку `CourseContentRevision(id=1, revision BIGINT)` и пять
PostgreSQL statement-level триггеров: `Course`, `TrainingDay`,
`Step`, `DayOnCourse` и `StepOnDay`. При INSERT/UPDATE/DELETE версия
растёт **в той же транзакции**, что и изменение. При ROLLBACK версия
откатывается автоматически. Даже прямое редактирование через Prisma,
минуя Trainer Panel, инвалидирует кэш.

Читатель перед использованием cached-content проверяет пару
`PostgreSQL revision + Redis revision`. Если пара изменилась, локальный
кэш очищается. Потеря Redis INCR **не влияет на консистентность**
последующих чтений, поскольку PostgreSQL-версия остаётся авторитетной.
При недоступном SQL-запросе версии кэш **обходится**, а не возвращает
устаревшие данные. Права доступа и прогресс остаются некэшируемыми.

**Важно при rollout:** сначала развернуть PostgreSQL-миграцию, и только
затем включать `ENABLE_COURSE_CACHE=true`. Если схемы версии нет,
читатели безопасно обходят кэш, но получают дополнительную ошибку
проверки и сообщение в логах.

### Реальный локальный регрессионный тест

Применена миграция только к выделенной базе
`gafus_course_cache_live_20261015`. Запущен скрипт
`packages/prisma/scripts/local-course-cache-live-smoke.mjs` на
реальных localhost PostgreSQL и Redis DB 14 с **двумя независимыми
Node.js-процессами**.

**61/61 проверка успешно**, включая:

## Этап 8 — одна проверка версии PostgreSQL и повторная нагрузка (15.10.2026)

**Оптимизация:** ранее каждый cache-hit требовал Redis GET и PostgreSQL
SELECT версии. После транзакционной инвалидации SQL-версия — единственный
источник истины. Убран Redis GET перед чтением кэша: теперь выполняется
только `SELECT "revision" FROM "CourseContentRevision" WHERE "id" = 1`.
Публикация Redis при тренерских правках оставлена для совместимости,
но больше не нужна читателям. При недоступности Redis у читателя
кэш продолжает работать, изменения после SQL-коммита видны сразу.
При недоступной PostgreSQL-версии выполняется безопасный обход кэша;
метрика `bypassRevision`. Существующая `bypassRedis` сохранена
только для совместимости с мониторингом.

**Регрессии:** 63/63 тестов двух независимых процессов на настоящих
localhost Redis/PostgreSQL, в том числе Redis outage у читателя при
новом коммите, Redis outage у тренера и откат SQL-транзакции.
Hono HTTP: 25/25 тестов с реальным JWT, доступом и персонализацией.
Web: реальный route + Prisma, с тестовой NextAuth-сессией.
