## Целевая схема

- Container Jobs: обработка фото и видео, ограниченные параллелизм, время и повторные попытки. Сохранить token fencing, immutable outputs и уборку источников.
- Container Services: закрытый origin для CDN; GET/HEAD/Range, лимиты ответа, проверка origin-секрета, запрет исходников и неподписанных playlists. Cold instances, без постоянно зарезервированных вычислений.
- Cloud.ru CDN: собственный домен, TLS, проверка срока подписанной ссылки на cache HIT и MISS, контролируемое удаление кэша.
- Evolution Object Storage: отдельные закрытые бакеты для пользовательского медиа. Course bucket/CDN/signing остаются на Яндексе.
- Основной сервер: авторизация, durable jobs, выдача разрешений и прием результатов; без обработки и проксирования файлов.

## Реализация пользовательских файлов — дополнительный этап AI Commander

**Изменения локальные, production НЕ переключён.** Добавлены `packages/cdn-upload/src/privateUserMedia.ts`, `cloudruCdnPurge.ts`, маршрутизация загрузки/удаления в `uploadToCDN.ts`, отдельные durable cleanup scopes `questions` и `documents` с предельно узкими префиксами. Загрузки в Cloud.ru включаются только при `CLOUDRU_USER_MEDIA_ENABLED=true`. Яндекс продолжает обслуживать курсы, аватары, прежние объекты и любую загрузку, не подходящую под allowlist. Сохранённые в базе объекты новых типов получают строго валидируемые маркеры `cloudru:questions:...` и `cloudru:documents:...`. Сами маркеры не предназначены для UI.

Фото вопросов подписываются на чтении DTO в core (ответы, вложенные ответы, главный вопрос, результат загрузки), TTL до 1 часа; базы данных сохраняют постоянный маркер, не одноразовый URL. Для документов питомцев core проверяет ownerId до генерации временной GET-подписи; list/upload/rename/get DTO выдаёт свежую ссылку для Web/Mobile, скачивание через Web использует 307-редирект на приватный Cloud.ru S3 SigV4 без проксирования байтов. Для legacy Yandex остаётся старый путь. MIME контролирует расширение объекта, поэтому файл с обманным названием не может ошибочно остаться в общем публичном бакете. При Cloud-ошибке удаления документа DB запись не уничтожается и запрос может быть повторён.

Удаление учётной записи в core создаёт отдельные `AccountStorageCleanup` snapshot jobs для новых scope `questions`/`documents`; собственные префиксы и фотографии из чужих ответов учитываются в отдельных bucket-scoped операциях. Legacy-снимок `public` исключает новые маркеры. Для новых документов прямые временные S3 URL не используют CDN, поэтому CDN purge для этих двух scopes не нужен. Gallery/feed purge направляется в адаптер Cloud.ru только при явном endpoint `https://s3.cloud.ru`; Яндекс-процедура не может ошибочно подтверждать удаление Cloud.ru. `CLOUDRU_CDN_PURGE_API_VERIFIED` обязателен — адаптер намеренно не используется в production до доказательства API-контракта и получения отдельного CDN токена.

### Обязательные параметры для КАЖДОГО `GALLERY` и `FEED`

## Миграция уже существующих фотографий и видео: owner-scoped copy / verify (12.10.2026)

Добавлен **неразрушающий** операторский CLI `infra/cloudru/migrate-legacy-media.mjs` и тесты `infra/cloudru/migrate-legacy-media.test.mjs`. Ранее dual-provider cleanup обеспечивал право на удаление старых/новых объектов при удалении аккаунта, **но не переносил** существующие файлы на Cloud.ru. Новый инструмент закрывает отдельную задачу фактической передачи данных между приватными S3 bucket при смене провайдера.

### Режимы (не запускать пока нет подтверждённых credentials/приватных бакетов)

```sh
# 1. Read-only инвентаризация одного владельца из приватного исходного S3:
node infra/cloudru/migrate-legacy-media.mjs gallery '<ownerId>' --plan
node infra/cloudru/migrate-legacy-media.mjs feed '<ownerId>' --plan

# 2. Только после проверенных источника/назначения, dual cleanup и CDN:
# MEDIA_MIGRATION_CONFIRM=copy-only-owner-media  (устанавливать в защищённой среде)
node infra/cloudru/migrate-legacy-media.mjs gallery '<ownerId>' --apply
node infra/cloudru/migrate-legacy-media.mjs feed '<ownerId>' --apply

# 3. Независимая read-only проверка передачи каждого файла по SHA-256:
node infra/cloudru/migrate-legacy-media.mjs gallery '<ownerId>' --verify
node infra/cloudru/migrate-legacy-media.mjs feed '<ownerId>' --verify
```

**Требуемые env:** все `GALLERY_...` или `FEED_...` параметры из предыдущего раздела про двухпровайдерную очистку, в том числе `*_LEGACY_BUCKET_VERIFIED=true`, source endpoint Яндекса, подтверждённый старый ПРИВАТНЫЙ бакет и его отдельные credentials, новые credentials Cloud.ru и точный private bucket `gafus-gallery-private`/`gafus-feed-private`. Перед `--apply` дополнительно обязательны `*_DUAL_PROVIDER_CLEANUP=true`, `*_LEGACY_CDN_RESOURCE_IDS` либо независимый `*_LEGACY_CDN_UNCACHED_VERIFIED=true`, а также `MEDIA_MIGRATION_CONFIRM=copy-only-owner-media`. Все secrets только из внешнего защищённого окружения, не из репозитория/CLI аргументов. По умолчанию `--plan` **не пишет** в S3; `--verify` **не пишет** в S3 и проверяет SHA-256 каждой пары.

Безопасность: только точные префиксы одного owner (`albums/<id>/`, `users/<id>/` для Gallery и `posts/<id>/` для Feed), идентификатор с жёсткой валидацией, source bucket Яндекса не может быть `gafus-media`/`gafus-public` (там остаются курсы/аватары), назначение ограничено двумя конкретными приватными бакетами. Недопустимые ключи, неизвестные длины, повреждённая пагинация или слишком большой owner (`MEDIA_MIGRATION_MAX_FILES`, 1…5000) останавливают попытку до PUT. Каждый исходный HEAD и все байтовые Range-GET связываются с исходным ETag; видео до 1 ГБ передаётся последовательно частями по 8 МиБ через multipart, память процесса ограничена размером одного chunk. Завершение multipart использует `If-None-Match: *`; при сбое запускается abort незавершённой загрузки. Для небольших файлов — immutable PUT с `IfNoneMatch: '*'` и Content-MD5. **Никаких DeleteObject, ACL public, перезаписи, редактирования БД или изменения пользовательских URL**. Совпадающий по имени уже существующий объект никогда не перезаписывается: SHA-256 проверяется побайтно, конфликт блокирует migration. После любой копии целевой объект считывается по Range и сверяется SHA-256 с полученными исходными байтами и метаданными; исходный HEAD повторяется, чтобы выявить смену файла во время передачи. В stdout только агрегированные счётчики, без ключей, токенов и объектов пользователей.

**Важное условие безостановочного cutover:** эти проверки подтверждают соответствие копий только в момент инвентаризации/verify и не блокируют параллельные записи пользователей. Нельзя считать готовностью только однократный `--verify`, если приложение ещё пишет в Яндекс. Требуется фонова́я передача, затем контролируемый drain/маршрутизация новых записей на Cloud.ru и финальный повторный `--verify` по всем владельцам (включая недавно созданные объекты и служебные ключи) перед переключением чтения/CDN. Смена провайдера и CDN должна быть отдельной атомарной/канареечной операцией, с dual cleanup включённым до и после неё. **Настоящий dual-cloud E2E transfer на пользовательских файлах НЕ проводился**: legacy приватные bucket+credentials не предоставлены/не подтверждены, Cloud.ru IAM/Registry/CDN CORS заблокированы. В ручном staging test использовать только синтетические файлы.

Тестовый набор `pnpm test:cloudru-media` проверяет no-network контракты CORS, контейнерных manifests, CDN cache-HIT/auth и owner migration. Последний тест покрывает dry-run без записи, owner-bound key, запрет публичного/непроверенного бакета, отказ на конфликтах содержимого даже с одинаковым размером, idempotent retries, `--verify` без PUT, multipart >8 МиБ, abort при частичном сбое и SHA-256 каждой копии.
