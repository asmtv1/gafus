# План рефакторинга тестирования GAFUS

19 ноября 2026 года. План для web, mobile, панелей тренера и администратора, API, доменных пакетов, обработчиков очередей и инфраструктуры. Основание — локальная рабочая копия на коммите `04052d616`, включая незакоммиченные изменения. Числа ниже получены из файлов и настроек. Измерение покрытия кода, времени и стабильности прогонов входит в первый этап.

**Результат рефакторинга.** Из чистой копии разработчик запускает одну проверку своего пакета или тот же профиль, что и CI. Для выпуска известен перечень обязательных сценариев, версия приложений и фактический результат каждого сценария. Систему внедряем по десяти поставкам в разделе «Порядок внедрения». Поставки 1–5 дают работающий путь от исходного кода до браузерного результата. Поставки 6–10 распространяют его на проект и подключают к выпуску.

## Целевая архитектура и границы

**Тест принадлежит модулю, поведение которого он защищает.** Разработчик доменного пакета ведёт его unit- и интеграционные тесты. Команда приложения отвечает за компоненты и HTTP-контракты своего приложения. Сквозной сценарий принадлежит команде продукта, через которое входит пользователь. Владелец CI отвечает за выбор задач, изоляцию и сводку. В каталоге сценариев эти роли привязываются к существующему сопровождающему кода.

Целевые пути ниже появляются по мере переноса. Файлы существующих проверок со старыми именами продолжают работать через профиль владельца до подтверждения эквивалентности.

```text
apps/<app>/src/…/*.test.ts(x)             быстрые тесты, компоненты, HTTP-контракты с подменами
packages/<pkg>/src/…/*.test.ts(x)         бизнес-правила и адаптеры без внешних процессов
{apps,packages}/<name>/tests/integration/ интеграции конкретного владельца, *.integration.test.ts
{apps,packages}/<name>/vitest.config.ts   локальные настройки, пути импортов и окружение
tests/
  config/vitest/                         общие правила выбора, отчётов и покрытия
  catalog/                               critical.json, suites.json, inventory.json
  support/                               compose.yaml, запуск стенда, фабрики данных, адаптеры провайдеров
  e2e/web/                               playwright.config.ts, fixtures.ts, learner/, trainer/, admin/
  e2e/mobile/                            flows/common/, flows/android/, flows/ios/
  test_*.py                              существующие проверки инфраструктуры
scripts/qa/
  test-system.mjs                        вход в plan, run, report
  …                                      действующие специализированные сценарии
.github/workflows/
  ci-cd.yml                              действующие проверки и решение о выпуске
  testing-reusable.yml                   исполнение плана и сбор отчёта
  testing-nightly.yml                    вызов того же процесса по расписанию
.qa/testing/<run-id>/                     временные plan.json, отчёты задач, coverage и трассировки
```

**Правила зависимостей.** Боевой код не импортирует из `tests/`. В тестах отдельного пакета используют его публичную точку входа либо соседний модуль, если проверяется чистая функция. Общие фабрики возвращают тестовые данные, а бизнес-ожидания записываются в самом тесте. Специфические фикстуры курса или платежа остаются у домена до появления второго потребителя. Общие средства подготовки окружения загружает процесс запуска или интеграционный тест. Импорт фабрики для unit-теста не должен инициировать Prisma, Docker или сеть.

| Слой | Граница реального исполнения | Где заканчивается проверка |
| --- | --- | --- |
| Unit и компонент | Проверяемая функция, reducer, store или смонтированный компонент. Управляемые часы, подмены транспорта и нативных модулей | Возвращаемое значение, изменение состояния, видимое действие или отказ. Текст реализации читают только специально обозначенные архитектурные проверки |
| HTTP-контракт | Настоящий маршрутизатор Hono, сериализация, валидация и обработка ошибок. Домен можно подменить | Статус, публичное тело, совместимость клиента, вызов разрешённой операции. Тест с подменой Prisma не доказывает сохранение записи |
| Интеграция | Настоящие модули и нужный процесс PostgreSQL, Redis или Worker. Для теста платежа ответ внешнего провайдера задаёт тестовый адаптер | Запрос через рабочую точку входа, затем независимое чтение состояния. Проверяются повтор, конкуренция, откат и восстановление там, где они меняют результат |
| E2E | Собранное приложение, настоящий пользовательский ввод, API, тестовая БД. Для mobile — установленная сборка | Результат глазами пользователя после новой сессии, перезапуска или возвращения сети. Проверка SQL дополняет видимый результат для денег и прогресса |
| Эксплуатационная приёмка | Миграции, сборка, очереди после сбоя, совместимость версий, тестовые аккаунты провайдеров и физические устройства | Отчёт с точной версией и средой. Результат внешнего провайдера или устройства имеет собственную строку |

## Контракт запуска

Использовать существующие pnpm и Turbo для запуска и выбора пакетов по зависимостям. Команды ниже — предлагаемый интерфейс после внедрения. Существующие `pnpm test`, пакетные команды и обязательные шаги CI сохраняют прежний охват на период перехода.

| Команда | Что входит и какой результат нужен |
| --- | --- |
| `pnpm test:unit` | Vitest рядом с реализацией. Быстрые проверки бизнес-правил, клиентских состояний и поведения компонентов. Можно запускать один пакет, файл или сценарий. |
| `pnpm test:integration` | Настоящие связи между модулями. Для HTTP — реальный маршрут приложения. Для сохранения и фоновой работы — одноразовые PostgreSQL, Redis и реальный обработчик, где этого требует сценарий. |
| `pnpm test:e2e:web` | Playwright Test, собранные web и панели, настоящий тестовый API. Каждый сценарий создаёт свои записи и проверяет результат от лица пользователя. |
| `pnpm test:e2e:mobile` | Собранный Expo-клиент на Android и iOS. Пилот Maestro на обеих платформах с выбором платформы для локального запуска. |
| `pnpm test:ci` | Тот же набор команд с правилами для PR. Единый итог по каждому обязательному сценарию, длительности и причине сбоя. `pnpm test:coverage` формирует сводный отчёт по тестируемому коду. |
| `pnpm test:full` | Полная воспроизводимая регрессия для коммита. Команда формирует один план запуска для локального стенда и ночного CI. Результаты заданий с браузерами, эмуляторами и симуляторами собираются в общий отчёт, который показывает пропуск любой требуемой платформы. |

Общие настройки Vitest применять там, где совпадают окружения. Сохранить Node для серверов, DOM для web-компонентов и существующие подмены нативных модулей в быстрых тестах mobile. Node-тесты сборки, Python-проверки, проверки схемы, архитектуры и инфраструктуры подключить к общей сводке штатными командами. Playwright поддерживает независимые браузерные сессии и проверку видимого поведения, Expo документирует запуск Maestro на сборках приложения. [Vitest 4 для монорепозиториев](https://v4.vitest.dev/guide/projects) · [Практика Playwright](https://playwright.dev/docs/best-practices) · [Пример Expo с Maestro](https://docs.expo.dev/eas/workflows/examples/e2e-tests/)

### План, исполнение и отчёт

1. **`plan` определяет ожидаемый состав до запуска.** Пакетные команды и граф зависимостей берутся из pnpm и Turbo. `suites.json` связывает специальные наборы с командой, путями, профилем, платформой и ресурсами. `critical.json` задаёт устойчивый ID бизнес-сценария, владельца, обязательные проверки и профили. Для PR использовать фактическую базу целевой ветки, выбирать изменённые пакеты и их потребителей. Изменение схемы, lockfile, логики выбора, общего стенда или неизвестный путь, влияющий на исполнение, расширяет план. При недоступной базе сравнения выполнять полный применимый профиль. Чисто документальное изменение получает явную причину сокращения. Имена задач и причины выбора выводить в `plan.json`. [Фильтры и предварительный план Turbo](https://turborepo.dev/docs/reference/run)
2. **`run` исполняет одну задачу плана штатным инструментом.** Локально команда запускает выбранные задачи последовательно либо с ограниченным параллелизмом. CI распределяет тот же план по заданиям Linux, Android и macOS/iOS. Vitest и Playwright пишут структурированные результаты, Maestro — JUnit, для Node/Python и прежних shell-проверок небольшой адаптер сохраняет код выхода и собственный отчёт сценария. Один общий shell-код выхода подтверждает только зарегистрированный набор. Для поимённо обязательных случаев нужен результат соответствующего теста. Проверки без платформы получают явный статус отсутствующего окружения. Пакетный запуск с прямым фильтром, например `pnpm --filter @gafus/course-progress-server test:unit`, остаётся рабочим.
3. **`report` сверяет ожидаемое с полученным.** Ключ записи — ID проверки, платформа и часть набора. Запись содержит ID запуска, коммит, отпечаток плана, номер попытки, статус, длительность и путь к результату. Для mobile добавляются версия сборки и ревизия OTA, если она проверяется. Чужой коммит или план, потерянная часть, неизвестный дубликат, пустой обязательный набор, пропущенный обязательный тест и авария подготовки дают неуспешный итог. Общий запуск возвращает `0` при выполнении требований профиля, `1` при падении утверждения и `2` при неполном окружении или отчёте. Локальный запуск одного пакета явно помечается как частичный. Исходные JUnit/JSON, трассировки падений и краткая таблица доступны из CI.

Например, в `critical.json` сценарий `training.complete` связывает три обязательные проверки с независимыми источниками результата. При переносе имена тестов получают стабильную метку в заголовке. Переименование или удаление проверки без обновления каталога проявится при сверке.

| ID проверки | Подключаемый исходник | Смысл результата |
| --- | --- | --- |
| `training.complete.unit` | [Расчёт статусов](../../packages/core/src/utils/training.test.ts) | Последний обязательный шаг переводит курс в согласованное итоговое состояние |
| `training.complete.pg` | [Параллельное завершение и откат](../../packages/course-progress-server/src/trainingAtomic.realpg.test.ts) | Обе конкурентные операции и ошибка посередине транзакции дают ожидаемое число записей и правильные состояния. В отчёте нужны все три имеющиеся проверки файла |
| `training.complete.web` | [Исходный сценарий ученика](../../scripts/qa/chromium-web-learner-progress-e2e.cjs) → `tests/e2e/web/learner/training-completion.spec.ts` | Ученик нажимает кнопку, открывает новую сессию, входит снова и видит выполненный шаг |

Пример целевой записи в `tests/catalog/critical.json`. При планировании PR поле `workspaces` связывает изменение пакета с проверкой. Для `main` и ночного профиля этот критический сценарий выполняется целиком. В `suites.json` каждый ID из `requiredChecks` разрешается в пакетную команду, исполнителя и проверяемые имена случаев. Несуществующая ссылка останавливает построение плана.

```json
{
  "id": "training.complete",
  "owner": "@gafus/course-progress-server",
  "workspaces": ["@gafus/core", "@gafus/course-progress-server", "@gafus/api", "@gafus/web-vite"],
  "profiles": ["pr-affected", "main", "nightly"],
  "requiredChecks": ["training.complete.unit", "training.complete.pg", "training.complete.web"]
}
```

Старые имена тестов допустимы во время перехода через явное сопоставление файла и точного названия случая. Пакетные `include/exclude` дают каждому файлу один основной уровень. Отдельные наименования проверок в одном файле сохраняются. Покрытие кода, выбор пакета и повторный запуск в другом профиле не создают дополнительных бизнес-сценариев.

После внедрения разработчик сможет воспроизвести эти проверки из корня репозитория.

```sh
pnpm test:unit --package @gafus/core
pnpm test:integration --scenario training.complete
pnpm test:e2e:web --scenario training.complete
pnpm test:e2e:mobile --platform ios
pnpm test:ci --base origin/main --plan-only
pnpm test:full
```

Тонкий слой запуска разбирает эти параметры и передаёт исполнителю только допустимые для него аргументы. Фильтр с неизвестным именем завершается ошибкой. При `--plan-only` выводятся список, причина включения и окружение каждой задачи. В CI краткий отчёт печатает точную локальную команду повторения сбоя. Скрипты, которые сегодня вызывают `pnpm test` и `pnpm test:all`, сохраняют прежний охват. Полный профиль с эмуляторами вызывается через `pnpm test:full`.

### Жизненный цикл тестовых данных

1. Базовый стенд для Linux и Mac — выделенный Docker Compose в `tests/support/compose.yaml`. Каждый параллельный исполнитель получает уникальное имя проекта, свои временные тома, порты и учётные данные. В compose-конфигурации выпуска указаны PostgreSQL 15 и Redis 7, а существующий сценарий прогресса ориентирован на локальный PostgreSQL 18. Основной профиль совместимости начать с версии из конфигурации выпуска и при инвентаризации сверить её с фактически поддерживаемой версией. PostgreSQL 18 оставить дополнительным профилем для действующих проверок. Зафиксировать версии образов в одном месте. [Конфигурация выпуска](../../ci-cd/docker/docker-compose.prod.yml) · [Текущий запуск проверки прогресса](../../scripts/qa/training-atomic-isolated-pg.sh) · [Изоляция проектов Compose](https://docs.docker.com/compose/how-tos/project-name/)
2. Средство запуска создаёт окружение из разрешённых тестовых параметров, ждёт готовности сервисов и передаёт дочерним процессам только сгенерированные адреса БД, очереди и тестового API. Существующие проверки имени БД, роли и адреса сохраняются при переносе. Перед адаптацией прежний скрипт запускается со своим действующим ограничением. Если обнаружен посторонний адрес или отсутствует нужный сервис, выполнение останавливается до записи данных.
3. Интеграции поднимают схему из миграций репозитория. Миграционная проверка дополнительно разворачивает предыдущую поддерживаемую версию схемы, заполняет синтетические данные, применяет изменения и проверяет чтение старым и новым клиентом. Исторические проблемы воспроизведения фиксировать с точной миграцией, применять каноническую процедуру репозитория. Прогон через `db push` может подтверждать функциональную проверку на подготовленной схеме, но не миграцию. [Проверки версий миграций](../../ci-cd/scripts/verify-production-migration-ledger.test.mjs)
4. Фабрики создают роли, пользователя, курс и оплату с уникальными ID запуска и теста. Для гонок использовать независимые соединения и зафиксированные транзакции. Для web каждый случай начинает с нового браузерного контекста. Для native очищать состояние приложения по сценарию, задавать адрес тестового API, заранее проверять его доступность из эмулятора или симулятора. Провайдерские события отправляются только в тестовый адаптер. Подлинное подтверждение Apple/ЮKassa проверяется отдельным заданием в их тестовых контурах.
5. В завершение сборщик сохраняет диагностические данные без секретов и удаляет ресурсы только этого запуска. При отмене CI выполняется тот же шаг очистки. После аварийного завершения следующий запуск использует новое пространство. Зависшие локальные ресурсы очищаются по метке владельца и ID запуска. Два одновременных запуска и отмена одного из них входят в приёмку стенда.

Привязать результат к версии приложения, ревизии OTA и серверному коммиту. |

**Как подключить к существующему CI.** В `ci-cd.yml` добавить вызов `testing-reusable.yml` с именем задания `testing-required`. Внутри него сначала строится план, затем исполняются выбранные задачи, последним безусловно запускается сбор результатов. Отсутствующую часть обнаруживает сверка с планом, в том числе если исполнитель был пропущен по условию. На этапе включения добавить `testing-required` и в `needs`, и в явную проверку успешного результата у `deploy-production`, где сейчас используется `always()`. **Кэш и нестабильность.** Для быстрых детерминированных задач кэшировать штатный результат исполнителя с хэшем входов. Обёртка создаёт запись текущего запуска после его получения и отмечает попадание в кэш. Для интеграций с сервисами, браузерных и нативных E2E и релизной приёмки исполнять сценарии заново. Повтор сохраняет обе попытки. Для критических случаев успешный повтор после реального падения требует разбора до признания релиза готовым. Профиль переводить в обязательные после успешного повторного прогона с чистыми данными и контрольного падения при известном дефекте или отсутствии результата. Длительность пробного периода выбрать по частоте запусков и исходной нестабильности конкретного набора.

## Как оценивать эффект

- **Покрытие правил.** Для каждого критического правила перечислить значимые исходы. Например, повтор успешного платежа, поздняя отмена и возврат после продления — три разных ожидания. Цель для правил с приоритетом 1 — автоматическая проверка каждого согласованного исхода.
- **Покрытие кода.** Сначала получить исходные цифры по пакетам, включая исходники, которые тесты вообще не импортируют. Показывать строки и ветви отдельно, исключения для генерации и типов сделать явными. Начальный ориентир для изменённой чистой бизнес-логики — 90% ветвей, с пересмотром по результатам пилота. Сохранить более строгие действующие пороги. В PR показывать покрытие изменённых строк и непройденные ветви. Сохранять V8-покрытие в формате Istanbul JSON по каждой части, объединять его по нормализованным путям исходников с картами исходного кода и формировать LCOV и HTML. Сверять с перечнем тестируемых файлов пакета, чтобы нулевое покрытие осталось в знаменателе. Процент вычислять по объединённым счётчикам, без усреднения процентов пакетов. [Покрытие в Vitest 4](https://v4.vitest.dev/guide/coverage)
- **Доверие к результату.** В отчёте у каждого запуска есть коммит, окружение, ожидаемые и выполненные сценарии, пропуски и первая ошибка. Набор, который прошёл только после повтора, помечать как нестабильный. У временно отключённой проверки есть владелец, задача и срок возврата. Внешние проверки помечать как подтверждённые только для фактически испытанного окружения.
- **Скорость и поломки после выпуска.** Измерять время до первого полезного отказа в PR, длительность 95% прогонов, долю нестабильных запусков и дефекты, дошедшие до пользователей. Для каждого такого дефекта выяснять, какое поведение не проверялось или почему нужный тест не попал в запуск. По этим данным выбирать следующую область для расширения.

## Приёмка всего рефакторинга

- **Полнота.** На выбранном коммите каждый workspace и каждый постоянный набор вне workspace учтён. Для прежней команды есть прямой или эквивалентный запуск. Каждая строка исходной регрессии и общей приёмки связана с новым результатом или действующим специализированным процессом. Любое согласованное исключение имеет причину, владельца и дату пересмотра. Открытый критический сценарий оставляет соответствующий этап незавершённым.
- **Unit-покрытие.** Каждый продуктовый домен имеет список тестируемых правил, покрытие строк и ветвей с известным знаменателем и перечень значимых непокрытых исходов. Для правил приоритета 1 выполнена вся согласованная таблица состояний. На выборке денег, доступа и прогресса временная инверсия бизнес-условия вызывает ожидаемое падение. Для автоматически сгенерированных файлов и пакетов, проверяемых через потребителя, видна причина исключения из конкретного показателя.
- **Интеграции и E2E.** На двух независимых прогонах подтверждены сохранение, откат и повторы. Сценарии web, тренера, администратора, Android и iOS привязаны к сборкам. Миграции, совместимость старого клиента и обязательные проверки физического устройства или тестового провайдера имеют собственные результаты там, где этого требует выпуск.
- **Решение о выпуске.** Сводка собирается из фактических результатов с тем же коммитом и планом. Проверено, что ошибка, неожиданный пропуск и потерянный отчёт блокируют кандидат. Автоматический и ручной пути выпуска используют эту сводку по правилам версии. Правила публикации и отката проверены в тестовом окружении.
- **Эксплуатация.** Из чистого checkout разработчик может воспроизвести упавший сценарий по одной команде из отчёта. Результаты сравниваются с исходной точкой по скорости и нестабильности. Дежурный знает, где посмотреть первую ошибку и кто сопровождает сценарий. До закрытия миграции проверить очистку после отмены и параллельную работу двух исполнителей.
