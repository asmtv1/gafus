# Questions Photo V2 — локальный регрессионный прогон (29.10.2026)

## Причина дефекта

В обычном Hono на `127.0.0.1:3001` выключен `QUESTIONS_V2_MEDIA_ENABLED`, поэтому `POST /api/v1/questions/photos/reservations` закономерно возвращает `503 PHOTO_V2_UNAVAILABLE`. Простое включение флага без `QuestionV2MediaTask`, S3 и обработчика Sharp оставляет фото в `QUEUED`/`FAILED`. Архивные фото из другого окружения могут отображать `FAILED`; повторное обновление страницы их не восстановит. Для таких файлов предусмотрено явное сообщение о необходимости заменить фотографию.

## Изолированный работающий локальный контур

`http://127.0.0.1:5507/questions` (Vite) → `http://127.0.0.1:3002/api/v1` (полный Hono) → локальная PostgreSQL `127.0.0.1:5432/dog_trainer_design_20261012`, MinIO `127.0.0.1:9000/gafus-refactor-questions-test`, отдельный локальный обработчик Sharp. Прямой multipart POST в MinIO, статус в PostgreSQL, WebP 360/720, подписанный GET на локальные варианты. Не используются Cloud.ru Jobs, production S3/CDN, API `api.gafus.ru`, GAFUS Main и production deployment.

Обычные `127.0.0.1:5173` и Hono `3001` **не переключаются**: текущие аккаунты и сеансы на них остаются в прежней среде. Вход и cookie-сессия на `5507` отдельные. Vite-режим открыт только при *одновременных* `GAFUS_QUESTIONS_ISOLATED_QA=1`, `VITE_QUESTIONS_LOCAL_QA=1` и `GAFUS_WEB_DEV_API_MODE=local-hono`; Origin `5507` сервер принимает только при точном соответствии флагов локального хранилища и порта `3002`. Все остальные дев-режимы сохраняют прежние прокси и правила.

Запуск из корня Refactor:

```bash
zsh scripts/qa/questions-photo-v2-run.sh
```

Запуск требует локальных PostgreSQL и MinIO, приватного `.local-pg-scratch/nonprod-s3/credentials.json` с правами 0600 и существующей **только в этой локальной базе** аддитивной миграции `packages/prisma/migrations/20261028134000_questions_photo_v2/migration.sql`. Миграция выполнена для `dog_trainer_design_20261012`; резервная копия схемы до изменения: `.local-pg-scratch/questions-v2-local-20261029/schema-before-design.sql` (0600). Режим не выполняет миграции автоматически; при неправильной БД или S3 аварийно завершится.

Пройден реальный HTTP-поток: JWT login → reservation 201 → подпись multipart POST → MinIO → confirm → очередь PostgreSQL → локальный Sharp → READY → подписанный WebP GET 200. Chromium/Puppeteer: HttpOnly-cookie login, выбор фото в форме вопроса, публикация вопроса, фактическое отображение картинки, выбор фото в форме ответа, публикация ответа, `READY` и отображение второй картинки. Проверки выполняются под новыми синтетическими пользователями, удаляют свои записи и свои точные S3 keys. Не запускают тестов на production-данных.

При долгой обработке UI останавливает автоматическое опрашивание через ~3 минуты и предлагает повторную проверку статуса вместо бесконечной загрузки. `FAILED` не маскируется кнопкой, которая лишь повторяет GET, — для такого случая нужна замена файла.

**Ограничение:** результат относится к QA Web на `5507` и изолированной БД. Не означает автоматического устранения 503 на существующем `5173/3001` или восстановления старых `FAILED` файлов. Для реального переключения стандартного dev-стека требуется его согласованная настройка/перезапуск, а для production — отдельное разрешение и проверка внешней инфраструктуры.

## Повторный дефект на исходном Web 5173 (29.10.2026, ~19:19)

Проверен **именно** исходный рабочий контур Vite `127.0.0.1:5173` → Hono `127.0.0.1:3001` → PostgreSQL `127.0.0.1:55921/gafus_refactor_real_work_20261024` (локальная WORK-копия; никакой production-записи). У одного ответа импортированное фото `cloudru:questions:` из прежнего провайдера, а у другого сохранены `questions-v2:` и `READY` с WebP 360/720 в изолированном MinIO.

**Корневая причина второго, реально существующего изображения:** запущенный Hono импортировал устаревший `packages/core/dist/core/src/services/questions/presentPhoto.js`, который использовал `questionsV2PublicDelivery` и выдавал публичный `gafus-questions-public.s3.cloud.ru` вместо изолированного `127.0.0.1:9000`. В Chromium воспроизведён `net::ERR_BLOCKED_BY_ORB`, хотя HEAD обоих локальных объектов и подписанный GET возвращали HTTP 200. После сборок `pnpm --filter @gafus/types build` и `pnpm --filter @gafus/core build` и перезапуска **только локального Hono 3001** с сохранением прежнего окружения браузер успешно получил local signed URL, HTTP 200, `img.complete=true` и `naturalWidth>0`. Исходный Vite 5173 не останавливался и продолжает работать.

**Первое фото** имеет legacy-маркер из другого провайдера и в текущем локальном S3 отсутствует. Разрешённая read-only проверка исходного объекта на публичном S3 вернула `404`; менять production S3/CDN или автоматически переносить оригинал запрещено. В DTO вместо ошибочного `FAILED` используется `UNAVAILABLE`; Web и Mobile показывают, что файл из прежнего хранилища недоступен в этой копии, без бесполезной кнопки «Повторить». Если исходный файл будет предоставлен пользователем, его можно загрузить новым штатным потоком V2 — миграцию/подмену объекта без разрешения не делать.

**Повторная проверка основного Web:** браузерный Chromium/Puppeteer с одноразовой авторизацией проверил ровно проблемную страницу, локальную WebP-картинку и описание legacy-файла (`REAL_5173_IMAGE_DISPLAY=PASS`, `LEGACY_UNAVAILABLE_COPY=PASS`). Запрос `/api/v1/auth/me` возвращал 200 после входа; его 401 до авторизации не являлся причиной ошибочного изображения. HTTP API через Vite 5173: `UNAVAILABLE` для старого изображения и `READY` + URL localhost-MinIO + signed GET 200 для нового. Синтетические пользователи удалены. Локальный API оставлен запущенным. Вновь собранный Core не должен заменяться старым `dist` при следующем локальном старте без повторной сборки.

## Mobile parity — 29.10.2026

Одинаковый контракт Web/Mobile: `READY` → подписанные JPEG/WebP-версии (маленькая в карточке, medium во fullscreen); `QUEUED`/`PROCESSING` → ожидание и опрос статуса; `FAILED` → явное сообщение о замене исходника вместо фиктивного GET-retry; `UNAVAILABLE` → объект из прежнего провайдера без доступного оригинала, требует исходного файла; временный сбой загрузки GET → кнопка повторного получения актуального URL. Для Mobile исправлены `QPhotos` и предупреждение о недоступном legacy-файле, fallback теперь привязан к идентификатору **версии подписанной ссылки**, чтобы не переносить старые ошибки на новый URL. Опрос pending в `QuestionDetailScreen` ограничен тремя минутами; затем предлагается `Проверить статус фото`. Экран сохраняет полноэкранное листание и отдельную кнопку повтора именно для сетевого сбоя.

**Локальная конфигурация iOS/Android QA:** `apps/mobile/.env.local` и `apps/mobile/.env.development.local` направлены на `EXPO_PUBLIC_API_BASE_URL=http://127.0.0.1:3001` для всех обычных API и `EXPO_PUBLIC_CHAT2_API_ORIGIN=http://127.0.0.1:3003` только для Chat 2.0. Два Hono используют одну локальную рабочую копию PostgreSQL и совместимые JWT-ключи; на 3003 Questions V2 не был включён, поэтому прежнее направление всех Mobile-запросов туда возвращало 503 на резервировании фото. Никакие production адреса и облачные ресурсы не переключались. На физическом устройстве `127.0.0.1` означает **само устройство**, поэтому для физического тестирования необходим отдельно доступный тестовый API/S3 и корректный подписанный hostname; эта конфигурация предназначена для iOS Simulator на Mac. После изменения `EXPO_PUBLIC_*` перезапустите или полностью перезагрузите JS-бандл Expo, чтобы он получил актуальные значения.

Для `127.0.0.1:3001` добавлен `scripts/qa/questions-photo-v2-real-work-worker.mts` с жёстким ограничением на локальную WORK-копию PostgreSQL `127.0.0.1:55921/gafus_refactor_real_work_20261024`, изолированный тестовый MinIO `127.0.0.1:9000/gafus-refactor-questions-test` и приватные dev-ключи из окружения Hono. Worker не разрешает подключение к production, не изменяет чужие S3/Cloud.ru Jobs, пишет лишь локальные QA-данные. Локальный worker должен работать одновременно с Hono при загрузке новых фотографий; без него после `confirm` останется `QUEUED`. Локальный безопасный запуск/проверка/остановка из корня Refactor: `python3 scripts/qa/questions-photo-v2-real-work-control.py start|status|stop`. Управляющий скрипт запускает только обработчик для этой конкретной локальной БД, сохраняет PID и не пишет секреты в вывод. Процесс отделён от временного QA-задания и продолжит работать, пока его явно не остановят или не перезапустят компьютер; после перезагрузки потребуется `start`. Тест `scripts/qa/questions-photo-v2-real-work-e2e.mts` проходит под отдельным синтетическим пользователем на `3001`, затем удаляет собственные запись и S3-варианты.

Результаты: типизация `apps/mobile` PASS (tsc exit 0); мобильные mounted тесты вопросов (41), тесты `photoDisplay`/`photoReadIdentity` (4) PASS, плюс локальный реальный HTTP-тест 3001 reservation→S3→Sharp→READY→signed GET PASS. Запущена отдельная QA-сборка `ru.gafus.qa.sim` в iOS Simulator, но интерактивная публикация с фото на iOS и Android-устройстве ещё не подтверждена; полный запуск всего набора Vitest `src/features/questions` упёрся в таймаут и **не считается PASS**. Не переносить эти результаты на production.
