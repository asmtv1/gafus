# GAFUS — приёмка релизного кандидата перед пушем в `main`

**Задание агенту.** Собери кандидат на актуальном `origin/main`, приведи workflow к текущей архитектуре, собери и запусти все доступные компоненты, пройди локальную приёмку и доведи исправимые сбои до повторного PASS. В конце передай точный SHA с одним из вердиктов раздела 12. Пуш в `main` запускает автодеплой после успешного CI. Сам пуш, merge, выкладка, включение флагов и публикация мобильного релиза остаются действиями владельца.

## 0. Порядок работы и полномочия

1. Выполняй этапы 1–3 по порядку. После чистой установки сервер, браузер, мобильные сборки и работа над workflow могут двигаться независимо. Тяжёлые сборки и нагрузочные тесты на одном Mac запускай по очереди. Внешние read-only предпосылки проверь в начале и повтори перед передачей.
2. Исправляй в кандидате причины падений, настройки запуска, Dockerfile, CI, конфигурацию тестов и фикстуры. Если важное поведение не покрыто, допиши минимальный автоматизированный тест или smoke с проверкой результата. Повтор каждого теста должен работать из чистого checkout по команде из отчёта.
3. После правки прогони исходно упавший тест, ближайший негативный сценарий и проверки потребителей. Присвой кандидату новый SHA. В журнале сохрани историю ошибки и исправления. Финальный обязательный набор должен заново пройти на итоговом SHA. Диагностические прогоны и результаты предыдущих SHA сохраняй как историю.
4. Продолжай доступные проверки при отдельном `BLOCKED`. Отсутствующий локальный инструмент, неверную переменную, конфликт порта, поломанный fixture или несовместимый запуск скрипта сначала попробуй восстановить. Вопрос владельцу нужен для выбора состава релиза, выдачи доступа, разрешения внешней операции или согласования изменений бизнес-поведения. Укажи затронутую проверку, конкретную зависимость и всё, что уже сделано локально.
5. Работай в отдельном кандидате. Локальные коммиты нужны для воспроизводимости. Сохраняй исходное рабочее дерево, чужие ветки, запущенные процессы и данные. В ходе приёмки используй synthetic fixtures, локальные сервисы и явно разрешённые тестовые интеграции. Секреты, дампы, cookies, полные подписанные URL и приватные карты исходников держи вне Git и итоговых логов. Чисти только ресурсы, созданные текущим запуском, по их записанным ID.

Проверь `promtool` на обоих наборах fixtures, старт Alloy с актуальной конфигурацией, валидность Compose и читаемость метрик API/Worker. Убедись, что новые сигналы существуют, неприменимые отключены, а legacy monitoring продолжает получать нужные ряды.
2. Собери поток `искусственный запрос → Hono → PG outbox → Worker → receiver`. По `operationId` найди все локальные звенья. Проверь, что logs/trace/metrics не раскрывают идентификаторы сессий, личные данные, signed URL, токены и ключи высококардинальных меток. Проверь устойчивый ACK после записи, повтор того же события, лимит батча, исчерпание бюджета и правильные счётчики.
3. Прогони offline Alloy E2E и очередь коллектора по `ci-cd/observability/uptrace/README.md`, включая `401/403`, `429/503`, неполный ACK, переполнение и рестарт. Фиксируй принятые и подтверждённые события до/после. Проверь отрицательный сценарий, в котором события не должны считаться доставленными, и путь реального восстановления без двойного эффекта. Подними локально Prometheus и Alertmanager и получи firing/resolved на test webhook.
4. Сравни baseline и кандидат на одном железе, одинаковых major PG/Redis, данных, профиле флагов, числе процессов, и concurrency. Зафиксируй 2 API + 2 Worker, warmup и по три одинаковых окна steady/burst. Сними p50/p95/p99, error rate, backlog/дубли, CPU/RSS и размер очереди. `scripts/qa/observability-load-median.mjs` в текущем виде маркирует результат как restore одного SHA. Для A/B используй общий расчёт медианы с отчётом, привязанным к двум SHA, либо допиши отдельный режим с тестом. Если разница близка к шуму, повтори в сопоставимых условиях. При ухудшении сравни DB планы, количество запросов и замеры по операциям, исправь найденное и повтори A/B. Одинаковый SHA до и после restore нужен для теста восстановления. Для сравнения релизов нужны два разных SHA.
5. Сверь, что автодеплой приложения не включает `GAFUS_TELEMETRY_PRODUCTION_APPROVED`, публичный экспорт private maps, Expo Observe или переключение remote write без отдельного согласованного релиза. Для действующей схемы мониторинга проверь, что прежние health/backup/alert сигналы сохраняются. Для включаемой в этот релиз внешней телеметрии нужны разрешённый nonprod readback, привязка к SHA, правила доступа и retention. Synthetic OTLP подтверждает локальные контракты. Для подтверждения native crash нужны стек и символика с реального тестового бинарника.

## 10. Переделать GitHub Actions под текущий релиз

Сохрани автоматический деплой после успешного CI на `push` в `main`. Рабочий артефакт этапа — изменённые workflow и их контракты в кандидате с проверкой графа jobs и действий операторов.

### 10.1. Общие проверки и передача артефактов

1. Сохрани действующие триггеры `push` и `pull_request` для `main`/`develop`. Все PR в `main` проходят полный набор CI для релиза, включая сборку и smoke семи образов без публикации. Для `develop` можно сохранить проверку затронутых пакетов с учётом транзитивных потребителей. Архитектурные границы, security, миграции, workflow-контракты и Mobile TS/JS выполняются всегда. Изменения lockfile, Prisma, общих пакетов, Docker или CI расширяют проверку до полного набора. Проверь достижимость тестов Worker, Bull Board, доменных пакетов и обоих media runtime.
2. Удали копирование разных последовательностей setup/install для одной платформы там, где это устраняет уже выявленный дрейф. Зафиксируй pnpm 10.12.4, значения Node major/patch по профилям из этапа 2 и frozen lock. Сохрани задачи, у которых есть собственный runtime контракт. Если fresh runner требует Prisma generate без ERD, используй опцию Prisma, подходящую текущей версии, с проверкой сохранности schema. Отсутствующий кэш должен приводить к нормальной установке/сборке. В существующем `cloudru-media-contracts` есть обязательный cache hit для compiled workspace. Замени его передачей проверенных build outputs того же запуска либо явной сборкой зависимостей в потребляющем job. Проверь cache-miss на чистом runner.
3. Сформируй production dist Web, Trainer и Admin из того же SHA в `build-apps`. Там же проверь App Links, private map contract и отсутствие `.map` в публичных деревьях. Передай три dist downstream через артефакт текущего запуска. Включи `.well-known` осознанно, проверь набор файлов и hash при распаковке. Артефакт должен содержать только публичный dist и контрольную информацию. В Docker job используй именно его. Private map upload разрешай только отдельным действующим условием и private bucket.
4. Везде, где повторно запускаются те же проверки, сравни назначения. Сохрани gates медиа, observability, release graph, migration и Chat2. Учитывай назначения существующих `ci-cd/scripts/*contract.test.mjs`. Меняй контракт только вместе с новой схемой работы и тестом старого запрещённого обхода.

### 10.2. Порядок автодеплоя и контракт манифеста

1. Путь `push/main` — полный CI → семь `linux/amd64` образов → проверка их runtime → манифест → production preflight → автоматический deploy. Независимые read-only preflight можно запускать раньше, но deploy зависит от них. При необходимости публикации для запуска smoke используй временную или SHA-привязку. Тег может служить для обнаружения артефакта. Источник для выкладки — digest, который проверил smoke.
2. Собирай результаты матрицы через отдельные артефакты по имени компонента и номеру attempt. Агрегатор принимает только семь ожидаемых компонентов из одного SHA/run/attempt, проверяет архитектуру, уникальность, полное имя репозитория, формат `sha256:<64 hex>` и результаты smoke. Минимальные поля итогового JSON — `schemaVersion`, `sourceSha`, `runId`, `runAttempt`, `images`, где `images` сопоставляет компонент с полным `repository@sha256:…`. Записывай итоговую контрольную сумму. Если частичный rerun оставил неполный набор текущего attempt, заверши без deploy и запусти заново весь workflow.
3. Передай в `production-deploy-reusable.yml` SHA и разрешённый манифест. Перед SSH и перед изменением Compose проверяй обязательные компоненты и текущий `origin/main` для штатного автодеплоя. Тяни образы по digest из манифеста. Если Compose требует локальный `:latest`, перетегируй локально только после проверки каждого скачанного digest. Сохраняй существующие registry tags для известных потребителей, пока их замену нельзя доказать. Путь выкладки должен работать, даже если удалённый `latest` указывает на иной образ.
4. `Deploy Only` берёт манифест из единственного верифицированного запуска `push/main` для запрошенного SHA. Проверь успешность обязательных jobs и происхождение артефакта с точным run ID и attempt. Redeploy допускает текущий SHA. Rollback разрешает прежний подтверждённый SHA с действующим schema compatibility guard. Сохрани возможность отката на действующий предыдущий релиз на переходе. Если он предшествует формату манифеста, подготовь и отдельно проверь его семь уже выпущенных digest по существующим доказательствам релиза, без восстановления ссылок по `latest`. Пропажа подтверждённых образов или доказательств отката — блокер до восстановления.
5. Сохрани общую production concurrency group между auto deploy, Deploy Only и другими изменяющими production операциями, где они разделяют ресурсы. Проверь действующий `Build Single Container` с его provenance, ограничением API-only diff и отдельной проверкой быстрого перехода. Если более новый SHA стал текущим, старый автоматический запуск завершает preflight без изменения сервера. Устаревший или параллельный run не должен начать миграцию поверх идущей выкладки. [Синтаксис GitHub Actions и concurrency](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
6. Сохрани последовательность `maintenance 503 → stop writers → backup → migrate → start → verify → reopen`. Продолжение cutover требует подтверждения остановки writer, снятие maintenance требует готового API/Worker и штатных сервисов. Частичное применение migration и failure в Cloud.ru sync/verify отражаются как разные этапы с точным результатом. Если приложения уже здоровы, а внешний Job update не прошёл, итоговый workflow фиксирует частичный выпуск и нужное ручное восстановление. Успешный deploy только VPS не должен скрывать упавший обязательный sync.

### 10.3. Production preflight, Cloud.ru, Beget и mobile workflows

1. Сохрани ограничения Chat2 cutover, Gallery redirect, Beget и Cloud.ru Jobs. Условный пропуск возможен только для веток поведения, уже предусмотренных действующим контрактом, с явной причиной. У отсутствующего обязательного результата итог fail. Chat2 QA guard читает первый `READY` в `docs/qa/CURRENT_RELEASE_STATUS.md`. Проверь отрицательный случай со старой записью и сохрани роль Markdown-статуса как veto. Для допуска дополнительно требуй свежий успешный CI на SHA текущего run. Старый `READY=YES` сам по себе не допускает релиз.
2. Сверь нужные GitHub environments и permissions. PR jobs выполняются с `contents: read` и тестовыми данными. Права публикации/секреты получает job, которому они действительно нужны, после проверки события и ветки. Для синтетической сборки `publish: false` убедись, что она работает без production Environment. Исправь найденный `actionlint` конфликт `required: true` и `default: false` в `cloudru-media-images.yml`. Сохрани обязательную передачу `publish`, удали неиспользуемый default, проверь все вызовы и оба режима.
3. Сохрани четыре ручных workflow Feed/Chat2 и независимый lifecycle двух media-образов. В штатном `main` workflow оставь предусмотренные проверки существующих четырёх Jobs и sync/verify в согласованном режиме. Изменения production Jobs, переключения CDN и публикация media-образов выполняются по их собственному действующему workflow и подтверждению. Проверяй совместимость новой app-версии с текущими media digest.
4. `gafus-sdk57-qa.yml` проверяет точный source SHA, мобильные зависимости, оба экспорта и private symbol inventory. Общие Mobile TS, тесты и Hermes exports должны блокировать `main` до выкладки. `gafus-self-hosted-ota-preview.yml` сохраняет ручной запуск, проверку native attestation, exact SHA и ограничения preview. Uptrace collector/Nonprod acceptance сохраняются отдельными QA операциями. Не подключай подпись, upload карт, OTA cohort, Store submission и включение Uptrace production к `push/main`. Сверь, какие из четырёх локальных workflow нужны кандидату и на какие скрипты, secrets/env имена и тесты они ссылаются.

### 10.4. Проверить workflow как исполняемую систему

Прогони `actionlint`, ShellCheck для скриптов и shell-блоков, сборку на чистом checkout и релизные контракты. Начальный набор команд:

```sh
actionlint -color=false .github/workflows/*.yml
bash ci-cd/scripts/production-schema-cutover.test.sh
node --test ci-cd/scripts/release-graph.contract.test.mjs \
  ci-cd/scripts/workflow-consolidation-contract.test.mjs \
  ci-cd/scripts/deploy-only-contract.test.mjs \
  ci-cd/scripts/cloudru-first-main-cutover-contract.test.mjs \
  ci-cd/scripts/workspace-dependency-graph.contract.test.mjs
node --test scripts/observability/check-workflow-release-gates.test.mjs \
  apps/mobile/scripts/verify-ota-preview-workflow.test.mjs
```

Добавь недостающую негативную проверку в существующий набор. Если выбор digest или preflight сложно проверить из YAML, вынеси проверяемую логику в узкий скрипт рядом с релизными скриптами. Для каждого случая запиши доступное доказательство из теста или реального разрешённого CI.

| Случай | Ожидаемое поведение |
| --- | --- |
| PR в `main`, push в `develop` | Положенные проверки проходят с чистой установкой. У задач нет доступа к production mutation/registry publish. |
| `main` push, CI PASS | Полный набор сборок, smoke, точный manifest, preflight success. Достижим один автоматический production deploy. |
| Не прошёл lint, audit, build, тест миграции, smoke, observability или media gate | Production deploy недостижим. Вывод CI показывает причину и job, который остановил выпуск. |
| Обязательный job стал skipped/cancelled, кэш пуст, PR diff не вычислен | Пропуск обязательного job останавливает deploy. Cache miss восстанавливается. Невозможность вычислить diff приводит к полной проверке. |
| Пропущен/дублирован компонент, меняется SHA, run, digest, платформа или набор dist | Агрегатор или deploy guard отказывает до внешних изменений. |
| Неверен provider config или не пройден Chat2 gate | Production preflight останавливает rollout с указанием причины. Предусмотренный conditional no-op проверяется отдельно. |
| Два запуска или stale SHA | Старый run выполняет только допустимые проверки, выкладка остаётся последовательной и привязана к подтверждённому SHA. |
| Ручной redeploy, rollback, fast-forward API-only | Верный сценарий проходит guards, несовместимая схема, неподтверждённый манифест и запрещённый diff дают отказ. |
| Сбой после миграции или на этапе Jobs | Работает предусмотренная ветка rollback/maintenance. Частично выполненные шаги отражены с действиями по восстановлению. |

В удалённом тестовом запуске используй PR или выделенную ветку только при наличии авторизации на такой push. Если доступа нет, выполни локальную репетицию CLI и контрактов до конца и отдельно отметь GitHub execution как внешний блокер оценки автодеплоя. Хостовый `actionlint` подтверждает синтаксис и статические выражения. Реальное окружение GitHub подтверждается квитанцией запуска либо отдельно проверенными настройками для конкретной job.

## 11. Закрыть предпосылки автоматической выкладки

Веди таблицу `проверка / требуется для этого пуша / доказательство / блокер / действие`. Начинай сверку параллельно с локальным прогоном, повторяй для итогового SHA. Используй только доступные и разрешённые read-only проверки. Когда нужен внешне изменяющий шаг, передай владельцу точный blocker и ожидаемый результат.

| Проверка | Доказательство перед вердиктом |
| --- | --- |
| GitHub | Точный head `main`, доступ к репозиторию, состояние Actions, доступные runners/квоты, production Environment и ожидаемые branch/approval rules. Нужен успешный CI на финальном кандидате в разрешённой ветке или PR без production side effects. Убедиться, что реальная настройка допускает выбранный автоматический деплой. |
| GHCR и VPS | Доступность pull предыдущего известного релиза, корректные имена образов, наличие места, работающий путь подключения и read-only данные о текущем SHA/версиях/health. Отметить, что release digest нового кандидата появляется после публикации. |
| GitHub secrets/vars | Перечень имён из реально используемых workflow и наличие в нужном environment. Одно наличие имени подтверждает настройку. Доступ и пригодность проверяются разрешённым read-only preflight или прогоном. |
| Chat2, Cloud.ru и Beget | Реальный destination Chat2 config, ожидаемый WSS, требуемые флаги и нативные minimum versions. Два Cloud.ru project/registry, четыре Jobs, их digest/статусы и совместимость. Применимые token/ACL/GET/HEAD/Range/CDN проверки из текущего пути релиза. |
| PostgreSQL и хвост восстановления | Действующий PG major и схема, место, свежий бэкап или рабочий путь его создания, предыдущие образы, проверенное поведение DB-03/05/06. Сохрани порядок действий оператора при сыром сбое и при уже применённой миграции. |
| Совместимость активных клиентов | Проверены серверные маршруты, необходимые старым поддерживаемым версиями Web/Mobile, в том числе при выключенных preview-флагах. Новая нативная версия не должна быть предварительным условием существующего пользовательского потока без явно утверждённого перехода. |
| Платежи, SMTP, push и телефония | Локальные side effects подтверждены на sink/fixtures. Для изменившегося активного внешнего контракта есть применимый test-only/live read-only результат либо статус `BLOCKED`. |
| OTA и Uptrace | Если это отдельные, выключенные режимы, проверить локальные миграции и отсутствие автоматической активации, отметить самостоятельные release blockers. Если любой режим включается этим выпуском, нужны его отдельные preview/production gates до статуса готовности. |

Первичный список можно сверить с `docs/deployment/ota-cloud-ru-s3.md`, `ci-cd/observability/uptrace/WORKFLOWS-AND-SECRETS.md` и действующим workflow. В них есть исторические примеры. Факты о доступе, flags, provider health и активных SHA перепроверяй.

## 12. Повторить приёмку после исправлений и передать владельцу

### 12.1. Как доводить сбой до закрытия

| Симптом | Действие агента | Что закрывает проверку |
| --- | --- | --- |
| Build, TS, lint или audit упали | Воспроизвести в чистой копии. Исправить реальную несовместимость, зависимость, генерацию или исходный код. Для fix lockfile проверить diff разрешённых версий. | Тот же шаг выполняется с exit 0, проверки потребителей и policy pass. |
| Контейнер собрался, процесс умер или ready = 503 | Снять image inspect, CMD, stderr, первые ошибки по зависимостям. Исправить ENTRYPOINT, runtime exports, native libs или config. Если guard честно блокирует ошибочный config, поправить тестовые параметры. | Новый образ из итогового SHA выполняет реальный сценарий. Есть health, отказ зависимости, восстановление и полезный запрос/задача. |
| Ошибка миграции, drift или rollback | Найти точную миграцию, checksum и состояние до/после. Если schema отличается от механизма обновления, дописать корректный forward path и fixture данных. Повторить на чистой копии baseline. | Fresh и upgrade проходят отдельно, второй deploy идемпотентен, восстановление репетировано. |
| Нулевой test count, `skip`, неизвестная команда или устаревший runner | Сверить manifest, filters и список тестов, найти активный entrypoint. Восстановить prereq или перенести проверку на рабочий isolated entrypoint, сохранив условия безопасности и assertions. | Выполнен исходный сценарий и нужное число проверок. У оставшихся skip есть проверяемое обоснование. |
| Поведение UI/API/Worker расходится с ожиданием | Снять минимум шагов, роли, fixture, request/response и эффект. Добавить регрессионный тест для сломанного поведения, исправить owning layer. | Нормальный, отрицательный и повторный сценарии проходят. |
| Сборка Mobile прошла, приложение не запускается | Разобрать crash/logcat, toolchain, native модули, подпись/entitlements, assets и network origin. Исправить исходный Expo plugin/профиль и заново сгенерировать проект. | Из итогового SHA собран и запущен свежий артефакт, crash не воспроизводится, native и JS checks проходят. |
| Сломан или пропущен workflow job | Проверить event/ref, `needs`, outputs, `if`, доступ, cache miss и целевые данные. Исправить graph/runner и добавить контракт на сбой или skip. | Положительный CI сценарий достижим, все запрещённые ветки блокируют выкладку, действие повторяется из чистой копии. |
| Нет внешнего доступа, credential, устройства или разрешения | Выполнить независимые части, записать идентификатор недоступной операции, доказать локальные условия. Подготовить точное действие для владельца или оператора. | Получен проверяемый внешний результат либо сохранён `BLOCKED` с объяснением влияния на данный push. |

Запрещённые способы закрытия дефекта — удалить проверку, проставить `continue-on-error` у обязательного шага, изменить ожидание теста под неверный ответ, вручную подставить `READY/VERIFIED`, переиспользовать чужую БД или тихо увеличить таймаут до исчезновения симптома. Для обоснованного изменения ожиданий укажи источник продукта и проверку совместимости.

### 12.2. Финальный прогон

1. Сверь полный diff от базы и `git status`. Если workflow сохраняет Markdown veto, обнови `docs/qa/CURRENT_RELEASE_STATUS.md` по результатам завершённого проверочного прогона **до** финального коммита. Затем создай финальный локальный commit и новый `RUN_ID`. Заново проверь чистую установку, обязательные сборки, тесты, миграции, runtime, логические и внешние gates по применимости. После финального прогона зафиксируй вердикт во внешнем отчёте без изменения кандидата. Любая последующая правка требует нового SHA и повторной приёмки.
2. Перед передачей повторно получи удалённый SHA `main` и выполни проверку ancestry. Если база сдвинулась, интегрируй новый `main` в кандидата, повтори затронутые сценарии немедленно и обязательный набор на новом SHA. Финальный кандидат должен быть отправляемым fast-forward на проверенной базе.
3. Перенеси результаты в итоговый отчёт рядом с логами. Закрытые исторические результаты оставь в истории. Повторная запись календарной даты или старого `READY=YES` не заменяет свежую квитанцию.

### 12.3. Форма передачи

```text
База origin/main:
Итоговый SHA и локальная ветка:
Время и RUN_ID:
Обязательные проверки: PASS … / FAIL … / BLOCKED …
Сценарии из новых изменений без доказательства:
Сборки: 7 основных образов, активные media-роли, iOS, Android
Фактический запуск: компоненты, health, пользовательские действия
Prisma: fresh, upgrade, обратная совместимость, восстановление
CI: логи, run ID при наличии, манифест/доказательства smoke
Mobile / OTA / Uptrace: что проверено и где
Исправления: причина → commit → тест → повторный результат
Открытые условия: проверка → кем/как закрыть → влияние на push
Вердикт:
```

Приложи `results.tsv` с колонками `id, компонент, сценарий, sha, окружение, команда, ожидаемый результат, наблюдение, exit, статус, лог`. Отдельно приложи image IDs/digest, список миграций, логи cold starts, QA matrix ролей, квитанции `33/5/A2/A3/18`, правило выбора rollback и подтверждение текущего `main`. Каждое доказательство должно быть доступно владельцу по локальному пути или ссылке на разрешённый CI запуск.

- **ГОТОВЫ К ПУШУ В `main`** — финальный кандидат основан на актуальном `main`, обязательная приёмка и применимые preflight закрыты, исправленные этапы подтверждены новым прогоном, нет открытых обязательных `FAIL / BLOCKED`, старые клиенты совместимы, порядок восстановления проверен. Указать при этом, какие отдельные ручные OTA, Store или telemetry релизы ещё требуют своей приёмки.
- **ЛОКАЛЬНО ПРОВЕРЕНО, ПУШ В `main` ЗАБЛОКИРОВАН** — обязательная локальная приёмка завершена, осталось внешнее условие с конкретным владельцем и действием. Перечислить проверяемые факты, которых не хватает.
- **К ПУШУ В `main` НЕ ГОТОВЫ** — хотя бы одна обязательная локальная проверка упала или не завершена. Указать точную ошибку, попытки устранения, затронутый кандидат и следующий шаг.
