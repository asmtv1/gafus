## Изменения

- Локальный `NEXT_PUBLIC_SITE_URL` в игнорируемом `.env` заменён с неработающего `localhost:3002` на Vite `http://127.0.0.1:5173`. Это **локальная настройка**, в Git не попадает. При следующем запуске Backend окружение необходимо перечитать; специальный сервер на `3001`, используемый другими тестами, не перезапускали.
- Восстановление пароля: CAS/throttle по `passwordResetRequestedAt` (2 минуты), новый хеш токена сначала создаётся без удаления прежнего. После подтверждённого принятия письма удаляются старые токены. При ошибке отправки удаляется только новая запись, прежний токен сохраняется и таймер ограничителя возвращается к предыдущему значению. Одноразовый срок действия — 1 час.
- Смена email: ссылка (24 часа) теперь сохраняется в БД **перед** обращением к почтовому провайдеру. При ошибке отправки удаляется только подготовленная запись; прежняя подтверждённая ссылка остаётся действительной. После успешной отправки старые токены очищаются без удаления более поздних параллельных запросов.
- Дополнительная проверка текущего пароля для пользователей с установленным паролем (`passwordSetAt !== null`) на Backend + Web + Mobile; VK-only аккаунты без пароля по-прежнему могут менять email с подтверждением нового почтового ящика. API отдаёт безопасную бизнес-ошибку 400 при неверном пароле, без отправки письма.
- После успешного подтверждения смены email отправляется best-effort уведомление на **предыдущий адрес**. Сбой уведомления не откатывает транзакцию изменения email.

## Проверки и ограничения

Тесты Core, Web и Mobile дополнены регрессиями: отказ провайдера, сохранность ранее выданного токена, неправильный текущий пароль, уведомление предыдущего ящика, двойные отправки, UI/API контракт. Core и API собираются, проверки типов Web/Mobile проходят. Browser Playwright через MCP недоступен (HTTP 429); безопасная отправка настоящего письма на выделенный test inbox и полный end-to-end со ссылкой ещё не подтверждены.

Транзакция PostgreSQL и доставка через внешнего провайдера не могут быть объединены в одну атомарную транзакцию. В экстремальном случае ошибок на стадии очистки может временно остаться более одного действительного токена, хотя новые ссылки не теряются при обычных ошибках доставки. Для строгой exactly-once доставки потребуется отдельный transactional outbox; специально без согласования production DB такую миграцию не выполняли.
