# Моменты: публикация → /moments без промежуточных экранов

Статус: реализовано 29.10.2026 только в GAFUS Refactor (Web). Production не затронут.

## Контракт интерфейса

- После подтверждения Core publish request (HTTP с валидным editor DTO, статус pending или published) Web сразу вызывает переход на /moments. Это работает для text/poll, фото, видео, файлов из альбомов и сохранённых черновиков.
- Медиа со статусом pending не объявляются готовыми. За реальные статусы и прогресс отвечает уже существующая MomentPendingPosts в каталоге /moments (серверная выборка, фоновое обновление каждые 20 секунд при открытой вкладке).
- Отдельный MomentProcessingStatus и его тесты/CSS удалены, поскольку в ленте они дублировали интерфейс. После published не открываются ни экран обработки, ни экран «Публикация готова», ни страница отдельного поста.
- Старые прямые ссылки на owner-only редактор /moments/drafts/:postId при статусах pending или published перенаправляются на /moments после подтверждённого GET редактора. Черновики draft и failed остаются доступными для восстановления и редактирования.
- В списке черновиков pending-публикация ведёт обратно в /moments на существующий индикатор. В самом виджете MomentPendingPosts лишняя кнопка «Продолжить» скрыта для pending, поскольку прогресс уже показан на этой странице. Для draft/failed она сохраняется.
- При ошибке S3, 400/401/403/409/503 и неизвестном ACK перехода как при успехе нет. Повторные отправки продолжают использовать сохранённые идентификаторы черновика и idempotency keys; не создаётся дубликат поста.
- Обновление клиентского кеша после подтверждённой публикации выполняется независимо от навигации и не задерживает переход на /moments.

## Проверки

- Смонтированные тесты редактора, публикации с фото, фотоальбомов и опросов подтверждают прямой переход и точное число Core writes, отсутствие перехода при ошибке, а также возвращение старых ссылок pending/published на /moments.
- Тесты MomentPendingPosts проверяют серверный прогресс и сохранение восстановления draft/failed.
- TypeScript и Vite build — обязательны для финального прогона.
- Проверка в авторизованном Chromium остаётся отдельной задачей: ранее Playwright MCP отвечал 429.

## Mobile: паритет навигации (29.10.2026)

- Новая публикация уже использовала правильный native-flow: mobileFeedPublications.enqueue с последующим router.replace на вкладку Моменты. Это сохраняется. В отличие от Web, мобильная native/offline-очередь переводит пользователя в ленту после принятия задания локальной очередью, до ACK удалённого Core; локальные фазы uploading/processing/failed и retry показываются в ленте. Сетевую ошибку нельзя называть успешной публикацией.
- После подтверждённого сервером изменения существующей публикации (status pending/published, правильный владелец, версия и pendingRevision) теперь выполняется router.replace на вкладку Моменты вместо перехода на отдельную страницу поста. Не ждём завершения invalidateQueries; фоновая ошибка обновления кеша логируется, но не превращает подтверждённый успешный publish в ошибку.
- Для уже принятой публикации со статусом pending в карточке FeedPublicationQueue больше нет ложного действия «Продолжить редактирование» и нет router.push в редактор. Обработка и прогресс остаются непосредственно в ленте. Настоящие черновики draft/failed сохраняют рабочую кнопку продолжения.
- Старая прямая ссылка на feed/create?edit=:id для подтверждённого owner pending-status возвращает на вкладку «Моменты» без нового создания поста. Published-посты остаются доступны по своей обычной странице и явной функции редактирования; их не удаляли.
- Неверный или неизвестный publish ACK, ошибка загрузки, отмена/смена авторизованного аккаунта и failed не выполняют успешную навигацию. Для новой публикации ошибка enqueue оставляет форму открытой; Core writes и idempotency keys не подменяются.
- Реальная очередь Feed Media V2, backend API, S3/CDN, Cloud.ru Jobs и мобильные медиа-плееры не менялись.
