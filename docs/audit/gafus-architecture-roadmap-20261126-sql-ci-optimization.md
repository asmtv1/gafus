### TransactionalMailEvent
- The real append-only webhook supplies receivedAt from DB default, separate from provider occurredAt. Existing providerMessageId/occurredAt index does not match the rolling receivedAt reads used by monitor and Admin alert/list.
- 400,000 rows, 24h failure-count and latest-20 queries. B-tree receivedAt improved read but grew to 8 MiB and insert10k median went 24.406 → 35.133 ms. Composite (type, receivedAt) was faster for selective reads but 13,197,312 bytes. BRIN receivedAt was 24,576 bytes and avoided a broad scan. In the append-ordered experiment the count median 9.243 → 1.542 ms (3739 → 160 shared blocks); latest-20 9.272 → 1.514 ms (3742 → 163 blocks). Five rolled-back insert10k runs on matching tables gave 46.597 vs 42.976 ms, blocks 78901 vs 78919; timing variability does not demonstrate improved writes, but no material extra buffer cost in that fixture. Count equality 239. Another less orderly two-cycle fixture still showed BRIN 8.952 → 2.884 ms for count. Random physical order can reduce BRIN selectivity; validate on restored representative data.
- Added schema BRIN index and separate 20261127170000_mail_event_received_at_brin migration; no old migration edited. Transactional bounded build uses lock_timeout=1200ms and statement_timeout=8000ms. Real isolated 400k row test: incompatible writer lock caused timeout/rollback, index absent after failure, successful reapplication once unlocked, valid BRIN 24,576 bytes, all 400,000 rows retained. No production migration applied. Long or contended production table must fail closed and be scheduled/reconciled; do not mark migration resolved without verifying actual index.
