# GAFUS · Архитектурный аудит и пошаговый план рефакторинга

26 ноября 2026 года. База анализа — GitHub main, [коммит b9bfc537f](https://github.com/asmtv1/gafus/commit/b9bfc537f18610afe81016440ed9cd33dacc3229). План предназначен для реализации отдельными PR. Все пути к исходникам ниже указаны от корня монорепозитория.

## Решение

Сохранить один Hono API, один PostgreSQL, самостоятельный Worker, отдельные облачные видеозадания и существующие клиенты. Границы уже выдерживают довольно большую систему. Наибольшую отдачу сейчас дадут три изменения в работе с данными — пакетное чтение аватаров и прав в Chat2, компактный персональный каталог курсов и инкрементальная синхронизация прогулок. Отдельный приоритет — воспроизводимая сборка: без неё трудно доказать, какой код тестировали и какой попал пользователю.

Наибольший риск при изменениях несут переходы подписки, повтор доставки после потери подтверждения, отзыв доступа к медиа и совместимость установленных приложений. Переписывать эти подсистемы целиком дорого. Для каждой ниже указан маленький первый срез, проверка результата и момент удаления старого пути. Новый пакет имеет смысл, когда есть второй независимый исполняемый потребитель, ограничение среды или измеримая выгода для сборки. Для остальных изменений достаточно функции или файла рядом с существующим владельцем.

## Этап 0. Зафиксировать исходный результат и цену изменений

1. На старте серии записать SHA исходников, идентификатор развёрнутого образа, PostgreSQL major, build/runtime/fingerprint клиента и активные флаги сценария. Сверить локальный diff с main по файлам и существующим PR. GPS-патч, self-hosted OTA и CDN переносить только после определения, что уже включено в конкретную сборку. Не сливать расходящееся рабочее дерево целиком ради обновления плана.
2. На изолированном стенде создать один воспроизводимый набор без персональных данных. Chat2 — 1/10/60 комнат с разными, повторяющимися и отсутствующими аватарами, отдельно 1/20/80 курсов; каталог — 20/200 курсов с отзывами и глубокой структурой; прогулки — пустая история, 100/2000 записей, долгая поездка без сети, удаление со второго телефона. Добавить обычного пользователя, тренера, гостя и пользователя с отозванными правами.
3. Для каждого сценария снимать отдельно p50/p95/p99 HTTP, число SQL statements, rows/bytes, время ожидания соединения, размер ответа до/после gzip, число сетевых запросов. Для экрана снимать время до доступного действия, память, JS/CSS по сети или активность JS-потока на телефоне. Холодный и тёплый прогоны, пустой и заполненный кэш, одинаковые версии и конкуренция. На маленькой выборке p99 считать диагностикой.
4. Запустить не менее пяти пар A/B на одинаковых данных с чередованием порядка; записать разброс. Детерминированные бюджеты (число вызовов, строк, байтов, отсутствие дублей) блокируют сразу. Первоначальное предложение для задержки — обсудить при устойчивом ухудшении p95 свыше 5% и за пределами шума; при большем естественном разбросе увеличить выборку. Не покупать меньший p95 ростом ошибок, подключения к БД или объёма фоновой работы.
5. Хранить короткий результат при PR: фикстура, сценарий, SHA до/после, размеры и исход одного аварийного сценария. Обновлять имеющиеся профили `tests/catalog`, `scripts/qa`, `docs/performance`; для локального эксперимента достаточно отчёта PR. **Выход** — другой разработчик повторяет одну пару замеров и объясняет расхождение в пределах разброса.

## Этап 1. Сначала исправить воспроизводимость сборки

1. В `turbo.json` сопоставить для Web, Admin, Trainer и API рабочий entry, config, HTML, публичные файлы, общий build-скрипт и реальные каталоги результатов. У Trainer Vite создаёт `src/trainer-vite/live/dist`, тогда как глобальный build декларирует `dist/**`, `build/**`, `.next/**`, `coverage/**`. Отдельно сверить скрытые production source maps и их выгрузку по SHA.
2. Исправить входы Web/Admin так, чтобы изменённый Vite-конфиг или входной HTML обязательно менял ключ. Для Trainer учесть вложенный output. У API проверить `tsup.config.*`, у Prisma — связь с `prisma:generate`, у mobile — отдельные jobs EAS/Metro и файлы `app/`, `plugins/`, `patches/`, native config. Использовать package-specific настройки там, где структура действительно отличается. Общая маска всех файлов монорепо сделает кэш бесполезным.
3. В одноразовой копии выполнить cold build → warm build → изменить по одному входу → build → удалить только результаты сборки в этой копии → восстановить из кэша. Сравнить содержимое HTML, JS, ссылок на чанки и фактического каталога Trainer. Для Prisma изменить тестовое поле в копии и проверить доступность типа после generate/build/typecheck. Различать прямые входы и транзитивные зависимости. Сохранить вывод `--dry=json` и проверку артефакта.
4. В `.github/workflows/ci-cd.yml` проверить связку cache key, restore-keys, скачиваемых `packages/*/dist` и фактического image build. Ключ prepare-deps учитывает lockfile и src, но в кэш входят также результаты компиляции. Развести кэш скачанных пакетов и пригодный для выпуска компилированный артефакт. При несовпадении исходных входов пересобирать нужные пакеты. Сначала проверить на одном CI job, затем убрать дублирующие ручные сборки с тем же результатом.
5. Оставить один обязательный запуск каждого архитектурного правила до сборки в том пути CI, которому он нужен. Удалять повторные проверки между jobs только после сверки DAG, отдельного single-container и OTA workflows. Сравнить cold/warm wall time и стоимость попадания в кэш. **Выход** — изменение любого реального входа инвалидирует ожидаемую задачу, чистое восстановление даёт работающий артефакт, пустой повтор обходится дешевле.

## Этап 2. Убрать глобальные регистрации по одному рабочему сценарию

1. Начать с `scripts/check-api-composition-installs.mjs`. Сейчас правило сравнивает найденное в `app.ts` с первоначальными 34 путями, их число может вырасти за счёт возвращения исходного элемента. Оно также ориентируется на текстовую форму одного импорта. Зафиксировать текущий уменьшающийся список. Добавить отрицательные тесты для возвращённого регистратора, импорта по другому пути/в роутере и второго экземпляра приложения. Рабочий пример пропуска — `routes/v1/reminders.ts` → `install-ag4-review-rows.review.ts`.
2. В первом рабочем срезе взять три регистрации auth — registration context, credential registration, registration contract rows. В main уже есть файлы `*-instance.ts` и части явной передачи. 6. **Выход** — один источник решения на класс медиа, отсутствие лишних запросов в успешном пути, разрешённый fallback действительно восстанавливает воспроизведение, отозванный доступ закрывается в заявленный срок. Beget/dual purge и старые домены снимать по отдельным условиям реестра. Успешная раздача Yandex сама по себе не доказывает возможность удалить старые квитанции.

## Этап 14. БД, наблюдаемость, CI и восстановление сервиса

1. **SQL.** Для медленных операций взять топ SQL по суммарному времени, p95 запроса API, числу вызовов и блокировкам. На репрезентативной обезличенной копии сравнить `EXPLAIN (ANALYZE, BUFFERS)` для чтений: количество просмотренных/возвращённых строк, сортировку, временные файлы, индекс и размер рабочего множества. Индексы добавлять под проверенный порядок WHERE/ORDER BY, измерить также время INSERT/UPDATE и размер индекса. Если выигрыш только на пустой таблице, изменение не принимать.
2. **Совместимая миграция.** Новое поле/таблица → версия API, читающая старое и новое → ограниченный повторяемый backfill с курсором → сверка строк и значений → переключение читателей → остановка старых писателей → удаление старого поля отдельной версией. Отдельно проверить lock/statement timeout на больших таблицах и остановку backfill. Сверить `ci-cd/scripts/verify-production-migration-ledger.py`, fresh-chain для используемой major и обновление со snapshot предыдущего релиза. Не переписывать опубликованные файлы миграций для улучшения структуры.
3. **Кэши.** Для HTTP, Redis, памяти процесса, TanStack Query, SQLite, CDN и TTL подписанной ссылки указать ключ, владельца, условие обновления и поведение при недоступности. При logout и смене аккаунта очистить именно данные владельца, при смене роли переоценить доступ на сервере. Проверить одновременно два API-процесса, один устаревший кэш, две вкладки Web и телефон без сети. Кэш корпуса курса и кэш права пользователя имеют разную область действия.
4. **Трассировка.** Использовать существующие `logger`, `error-handling`, `ci-cd/observability/uptrace` и `scripts/observability`. Сопоставить клиентскую версию/OTA → HTTP request → транзакцию → outbox/job → внешний ACK на одном тестовом действии. Ввести только недостающие интервалы: ожидание очереди, время провайдера, ожидание пула, время первого кадра. Метки ограничить доменом/маршрутом/сборкой/классом исхода; личные идентификаторы, токены, координаты и signed URL в метки не помещать. Замерить накладные расходы экспорта и поведение при отключённом коллекторе.
5. **Сигналы для эксплуатации.** Проверить на стенде сценарии «reset-письмо застряло», «подпись OTA отклонена», «обязательная ревизия не завершает установку», «ревизия CDN не очищена», «outbox стареет», «запись GPS стартовала без точек». Для каждого — метрика с правильным знаменателем, ссылка на обезличенную трассу, ответственный и безопасный способ восстановления. Отдельно проверить ложную тревогу при отсутствии трафика, задержанный экспорт и реальное срабатывание уведомления. Не плодить панели с одинаковым ответом.
6. **Восстановление.** `backup-to-yandex.sh` проверяет байты резервной копии; `scripts/qa/observability-restore-rpo-rto.sh` проверяет часть восстановления БД. На изолированной среде восстановить snapshot, поднять API и Worker, проверить авторизацию, приватный курс, прогулку, одну outbox-запись, согласованность медиа и доступность предыдущего подписанного OTA. Записать RPO как возможный интервал потери подтверждённых записей, RTO — до работоспособного пользовательского сценария. Сверить с согласованными продуктовыми пределами. Один успешный pg_restore не завершает испытание.
7. **Тесты и управление стоимостью.** Использовать `tests/catalog/critical.json` и готовые профили. Изменение чистой функции — unit; публичный контракт — смонтированный HTTP/обе стороны; транзакция/lock — настоящий PG; отказ Redis/очереди — recovery; native — физическая release-сборка. Быстрый набор для PR, длительный для nightly, критичные затронутые профили — требуемый статус для выпуска. Сравнить время ожидания PR и flaky rate. Когда две проверки защищают один и тот же инвариант, оставить более информативную; удалить тесты, которые фиксируют только старое имя или число файлов.
8. **Выпуск и откат.** Для API/Worker использовать совместимую схему и последовательность mixed-version; для контейнеров привязывать digest, для мобильного — подпись и fingerprint. Включить чтения сначала на ограниченной когорте, сравнить ошибки, длительность и результат; для денег сравнивать расчёт без второго внешнего эффекта. При нарушении остановить расширение, переключить чтение/обработчик, сверить очередь и сохранённые операции. Не откатывать БД разрушительным down после того, как новый клиент записал данные.

## Реестр удаления легаси и бойлерплейта

Для каждой строки назначить роль-владельца в PR и указать последнюю версию, которая ещё читает старый формат. «Ноль вызовов» имеет смысл при работающей телеметрии и известном общем объёме трафика. Период наблюдения покрывает TTL/lease/retry, rollback и максимальный срок возвращения поддерживаемого офлайн-клиента. Если такой срок не определён, миграционное чтение сохраняется до явного решения о поддержке. Удаление исполняемого пути и физическое уничтожение пользовательских данных — разные операции.

| Денежное событие и сообщение | Есть существующие PG-профили, текущую полную матрицу заново не прогоняли | Повторы/гонки дают один логический результат, нет второго списания, награды или раскрытия доступа. Есть recovery при неизвестном внешнем результате. |

Получены фактические RPO/RTO и перечень оставшихся ручных действий. |

### Что в этом проекте будет означать «10 из 10»

Это десять проверяемых критериев приёмки. Каждый закрывается своей ссылкой на код и результат проверки того же релиза. Непроверенный критерий остаётся открытым. Исходное число прошедших тестов не переводится в оценку архитектуры.

1. **Понятность.** Для основных сценариев по публичному входу видны функция с правилом, владелец записи и тест. Второй инженер может изменить один сценарий, не инициализируя всё приложение.
2. **Границы.** Нет циклов runtime-пакетов, случайного серверного кода в клиентах и скрытых глобальных установщиков в достижимом API. Каждый оставшийся инфраструктурный импорт находится там, где исполняется операция с БД.
3. **Стоимость чтения.** Для трёх приоритетных чтений/синхронизации зафиксированы SQL, байты и p95. Устранён показанный рост числа обращений, результаты воспроизводятся, соседние сценарии укладываются в согласованные бюджеты.
4. **Согласованность записи.** Конкурентные и повторные операции по оплате, прогрессу, чату, записи к тренеру и удалению дают ожидаемый итог в настоящей БД даже после рестарта.
5. **Права и данные.** Роль, владелец и приватность проверяются в точке решения; кэши и фоновые задания сохраняют их при logout, блокировке, отзыве и удалении аккаунта.
6. **Клиентский опыт.** Есть измерения загрузки и интерактивности на Web, iPhone и A53, корректный offline/reconnect и физическая проверка GPS/фона. Экраны разделены в местах, которые упрощают работу и дают измеримый эффект.
7. **Совместимость.** Указан диапазон поддерживаемых протоколов и бинарников, проверены предыдущий поддерживаемый клиент с новым сервером и новый клиент при rollback сервера. Нативные зависимости подтверждены артефактом.
8. **Эксплуатация.** Оператор по сигналу находит затронутый пользовательский сценарий, видит потерю/задержку/повтор и может подтвердить восстановление. Проверены отказ PG/Redis, очереди, провайдера и telemetry.
9. **Воспроизводимость.** Чистая и кэшированная сборки используют правильные входы. SHA, image digest, подписанный release/OTA и символы однозначно связаны. Проверены миграция вперёд, восстановление и рабочий откат.
10. **Завершённая миграция.** Для каждого временного пути либо удалены код, конфиг и тестовая обвязка, либо есть конкретный действующий потребитель, владелец и событие снятия. Дублирование не становится ценой успешного рефакторинга.

### Как проверить первые PR на существующих инструментах

Команды статических проверок и dry-run выполняются из корня. Для тестов с PostgreSQL/Redis нужны изолированные сервисы соответствующего профиля. Команды из следующего блока сверяют исходники и состав сборки.

```sh
pnpm check:core-boundaries
node scripts/check-workspace-graph.mjs
node scripts/check-mobile-core-boundary.mjs
node scripts/check-api-composition-installs.mjs
pnpm exec turbo run build --filter=@gafus/web-vite --dry=json
pnpm exec turbo run build --filter=@gafus/trainer-panel --dry=json
pnpm exec turbo run build --filter=@gafus/admin-panel --dry=json
node --test infra/cloudru/shared-yandex-cdn-readiness.test.mjs apps/mobile/scripts/native-release-contract.test.mjs scripts/observability/check-workflow-release-gates.test.mjs
```
