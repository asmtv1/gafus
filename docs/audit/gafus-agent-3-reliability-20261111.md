- У Chat2 уже есть транзакционный outbox, захват с lease и проверкой владельца, ограниченные повторы, DLQ и административный retry. Локально проверены конкурирующие процессы Worker, падение после ACK, takeover и дедупликация эффекта. - В коде есть восстановление Chat2/Feed медиа, политика повторов и отдельное отслеживание 360p. Локальный Redis/BullMQ проверял потерю ACK, PostgreSQL — просроченный lease и восстановление. Реальное исполнение Cloud.ru 360p, поиск запуска при потерянном ACK и обработка callback остаются открытыми.
- Локальные проверки доставки проверяли 403/404 и ACL с MinIO/прокси. Нужен единый тест с фактическим Beget edge в изолированном окружении. Чтение Cloud.ru через доступное подключение в предыдущем аудите завершилось ошибкой аутентификации. Стенд с безопасными ресурсами ещё требуется подтвердить.

Свежий общий регрессионный прогон записал 33/33 PASS, в том числе сборку и Worker. Изолированному медиа-прогону нужна своя квитанция.

## 6. Outbox, leases и защита от повторного эффекта

1. Сопоставить существующие состояния с `PENDING`, `RUNNING`, `RETRY_WAIT`, `COMPLETED`, `FAILED`, `DEAD_LETTER`, `CANCELLED`. Проверить наличие или однозначное отображение `id`, `type`, `operationId`, `idempotencyKey`, `status`, `attempts`, `maxAttempts`, `nextAttemptAt`, `leaseUntil`, `lastErrorCode`, `createdAt`/`updatedAt`. Опирайтесь на текущие outbox и очереди. Для Chat 2.0 сначала докажите пробел существующего механизма и исправляйте его адресно.
2. Для важных задач проверить атомарность commit/rollback бизнес-записи и outbox-события на PostgreSQL. Сохранять dispatch intent в локальной транзакции, внешние Cloud.ru/S3/HTTP-вызовы выполнять после неё. При rollout сначала расширить схему совместимой миграцией, затем перевести читателей и писателей и проверить rollback.
3. Проверить короткий конкурентный claim через `FOR UPDATE SKIP LOCKED` или действующий эквивалент, lease, heartbeat для длительных задач, takeover и fencing устаревшего Worker. Запустить два отдельных процесса и многопоточный SQL claim. Убедиться, что опоздавший Worker не меняет состояние и итог после takeover.
4. Проверить уникальные ограничения БД, когда они нужны. Для видео ключ должен описывать версию объекта, для Cloud Job — связывать intent, известный run и результат, для чата — защищать пару отправитель/`clientMessageId`, для уведомления — событие/получатель. Для Gafus сохранить идентификатор экономического события и атомарность списания, проверить передачу ключа в Worker. Списание и начисление на реальной изолированной БД принимает агент 1. Допускать повтор физической доставки с тем же идентификатором при единственном бизнес-эффекте.
5. Развести приоритеты и пределы конкурентности. Chat и изменение доступа — критичные, медиа и уведомления — операционные, аналитика — низкий приоритет. Проверить, что бурст транскодирования сохраняет доставку критичных событий и не создаёт голодания остальных очередей.

## 7. Retry, DLQ и восстановление

| Случай | Требуемое поведение |
| --- | --- |
| Timeout, 429, 500/502/503/504 | Ограниченные экспоненциальные повторы с jitter, учёт `Retry-After`, бюджет по типу задачи. Для потерянного ACK сначала сверка intent и эффекта. |
| 401/403, невалидный файл | Классификация и остановка автоматического повтора. Для отсутствующего объекта S3 проверить состояние загрузки и категорию ошибки. |
| Событие уже обработано | Подтвердить существующий эффект и завершить с сохранением ключа идемпотентности. |
| Попытки исчерпаны | Запись в DLQ с типом, operationId, попытками, нормализованным кодом, временем и ссылкой на диагностику. |

- Проверить безопасный ручной retry существующим административным путём. Проверить полномочия, аудит, повтор команды, конкурентное выполнение и повтор финансового эффекта. Если панель операций входит в итоговый объём, использовать действующий DLQ/API и ограничить интерфейс фильтрами, поиском по ID и историей.
- В reconciler проверять истёкший lease, известные Cloud.ru run ID и валидный результат 360p. При неопределённом ACK использовать dispatch intent, журнал попыток и проверку результата S3. Восстанавливать потерянные переходы после рестарта, не перетирать более новую версию и запускать повтор только при доказанном условии. Проверить дублированные, опоздавшие и пришедшие в другом порядке callback.
- Сохранить независимые состояния 720p и 360p, включая `NOT_REQUIRED`, `PENDING`, `PROCESSING`, `READY`, `FAILED` либо их действующее отображение. Публикация и воспроизведение 720p продолжаются при pending, сбое и retry 360p. Готовая 360p появляется в клиенте. Для CDN-first проверить разрешённые категории fallback, запрет fallback при 403/404 и соблюдение ACL при всех исходах.
- Разобрать 16 ошибок исторического медиа-прогона. По каждой повторить сценарий на общем исходном снимке и отнести к дефекту, тестовому окружению или устаревшей точке входа с доказательством. Если путь изменился, перенести тест на действующий Web/Mobile/API поток и сохранить исходные проверки эффекта. Повторить полный интеграционный медиа-прогон на изолированной PostgreSQL.

| 7 | Остановить Worker сразу после внешнего ACK, до локального подтверждения. Замена завершает операцию с единственным бизнес-эффектом. Проверить отдельно синтетический брокер и реальный Job на согласованном стенде. |

| 14 | Два реальных HTTP-запроса с одинаковым `clientMessageId` дают одну строку и один пользовательский эффект. Проверить изоляцию между отправителями и доставку через WebSocket. |
