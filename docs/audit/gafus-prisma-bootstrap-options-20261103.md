# GAFUS: безопасное начальное развёртывание Prisma (P3018) — решения и локальная проверка

Дата проверки: **2026-11-03**. Repository: `gafus-refactor`, HEAD `b4492e73e`. Это **проект решения, не готовая миграция** и не разрешение на изменения production.

## Фактическая проблема

На пустом **собственном** PostgreSQL 18 `prisma migrate deploy` завершается `P3018` / `42P01`: первая миграция `20241108120000_exam_result_trainer_review` пытается выполнить `ALTER TABLE "ExamResult"`, хотя эта таблица ещё не создана. История содержит **163** migration SQL. Нельзя «починить» её перестановкой/переписыванием уже применённых файлов: содержимое `_prisma_migrations`, контрольные суммы и поведение существующего production должны оставаться неизменными.

Из **текущего** `packages/prisma/schema.prisma` получен локальный, **не добавленный в Git** SQL-кандидат командой `prisma migrate diff --from-empty --to-schema-datamodel ... --script --output .gafus-refactoring/architecture-qa-20261103-local/bootstrap/current-prisma-schema-only-baseline.candidate.sql`. Размер **199 674 байт**, SHA-256 **`925b443719014dba348ac06ea9125d89b0a00f2a4660c02fd1008e15f9b449b5`**.

`node ci-cd/scripts/local-prisma-bootstrap-candidate.mjs` запускает **новый** PG18 cached Docker на случайном `127.0.0.1` порту, tmpfs, без `docker pull`, prod credentials или существующих баз; применяет SQL через реальный Prisma `db execute` и проверяет `migrate diff --from-url <fresh DB> --to-schema-datamodel ... --exit-code`: **PASS**, создано **186 таблиц**, datamodel diff пустой. Дополнительно проверено, что `_prisma_migrations` **НЕ** создана/не подделана. Контейнер после проверки удалён.

**Но это не готовая production baseline!** В исторических миграциях найдено **8 SQL-файлов** с `CREATE FUNCTION/TRIGGER/EXTENSION`, плюс data backfills/seed. Примеры: проверка неизменности цены/промокода (`20260812120000_add_app_subscription_promo_codes`), триггеры версионирования курсов (`20261015020000_course_content_revision`, `20261022153000_course_version_global_trigger`), запись намерений удаления Chat2-медиа (`20261027011000_chat2_media_deletion_ledger`), нормализация smart-feed. В кандидате **0 пользовательских триггеров** — `schema.prisma` не описывает их. Базовая структура совпала с Prisma, но регуляторные/финансовые и медиаданные-инварианты **не воспроизведены**. Нельзя считать `prisma db push` или `migrate diff == empty` доказательством эквивалентности исторического SQL и нельзя заранее помечать 163 миграции применёнными.

## Вариант A — рекомендован: отдельный versioned bootstrap для абсолютно новой БД

1. Оставить **все существующие** `packages/prisma/migrations/*/migration.sql` побайтно неизменными; старую production `_prisma_migrations` не трогать.
2. Подготовить versioned `bootstrap`-артефакт **только для новой пустой БД**, включающий: проверенный Prisma schema SQL, все *актуальные* bespoke функции/триггеры/индексы/extension из миграций, требуемые сиды и статические настройки. Данные пользователей/продукционные секреты не переносить. Отдельно зафиксировать checksum и ожидаемые количества SQL-объектов.
3. Использовать исключительно guard-процедуру с явным `NEW_DB_BOOTSTRAP=1`, UUID-именем целевой БД, ограничением на fresh/empty schema (таблиц 0, кроме system), отдельным операторским подтверждением на реальном релизе. Запретить путь для существующей БД, prod-хоста или БД с `_prisma_migrations`.
4. На **новой БД после полного воспроизведения всех объектов** зарегистрировать 163 неизменённых миграций как уже включённые в verified baseline через `prisma migrate resolve --applied <name>` **только при fresh bootstrap**, а затем запустить `prisma migrate deploy` и `prisma migrate status`. Отдельный manifest проверяет список и checksum файлов прежде чем «закрыть» старую историю.
5. На двух независимых ephemeral PG проверить: сравнение Prisma datamodel через `migrate diff`, полный каталог пользовательских триггеров и функций (`pg_trigger`, `pg_proc`), содержание сидов (без prod данных), инвариант финансового price snapshot, автоматический `Chat2MediaDeletionIntent` при SQL-delete, course version, создание/удаление Gallery, Questions и webhook replay. Добавить новый future SQL migration и доказать его применение; повторный bootstrap должен **отказываться** от непустой БД, а не изменять её.

**Статус A:** локально проверен *только* кандидат структуры, пункт 2 по custom triggers/backfill и пункты 3–5 не закончены. Можно безопасно продолжать разработку изолированно **без дополнительного разрешения**, пока не затрагиваются existing/prod. Для применения в реальном релизе нужен согласованный migration playbook.

## Вариант B — восстановление из доверенного checkpoint для новых инстансов

1. Оператор предоставляет **явно разрешённый** и независимо проверенный backup/checkpoint требуемой версии, содержащий **структуру, SQL функции/триггеры, историю миграций и необходимые static rows**. Если в нём могут быть пользовательские данные — потребуется отдельное решение об их безопасной очистке, хранении и доступе; без этого такой source вообще не брать.
2. Развернуть в новой одноразовой БД, проверить TOC, checksum, `pg_restore`, функциональные constraints и `prisma migrate status`; затем только новые forward migrations. Production copy, пользовательские данные и реальные учётные записи **запрещены** текущим поручением.
3. Не запускать архивированные SQL миграции с нуля: точка восстановления уже содержит их применённую структуру и запись migration journal.

**Статус B:** действительный источник checkpoint **не предоставлен** и получение real backup из prod запрещено. Никаких удалённых копий не запрашивалось и не скачивалось. Нужен пользовательский выбор/разрешённый источник, если решено использовать B.

## Критерии решения

Рекомендуется **A**, чтобы новый инстанс можно было создавать без доступа к персональным данным и непрозрачной backup-поставке. **До включения в релиз** пользователь должен утвердить стратегию A или B и конкретный план выпуска (но безопасная локальная разработка A может продолжаться заранее). Минимальное решение для A: разрешить *после завершения локального audited bootstrap* отдельный rollout/релиз при неизменённой истории существующих инстансов. Для B: дополнительно определить доверенный источник резервной копии и его границы данных.

**Запрет:** не запускать `prisma migrate resolve --applied` по текущему schema-only-кандидату; у него отсутствуют критические raw SQL triggers. Не выдавать локальный `db push` за восстановление migration history и не править production `_prisma_migrations`.
