# Chat2 reconnect-after-ban — verified local Centrifugo v6 proxy-only candidate

Status: **LOCAL QA CANDIDATE VERIFIED, PRODUCTION CUTOVER NOT APPROVED**. This is an actionable security finding, not a claim about live production.

## Proof of the current weakness (old token mode)

In a disposable real PostgreSQL 18 + Redis + Centrifugo 6.9.7, the app's `moderateGroup(..., "BAN")` called Centrifugo `/api/unsubscribe` and `subscriptionToken(bannedUser, room)` correctly refused a *new* JWT. Nevertheless, creating a new WebSocket with the still-valid room JWT issued just before the ban succeeded: `BANNED_USER_MUST_NOT_RECONNECT_WITH_OLD_SIGNED_ROOM_JWT: expected true to be false`. Evidence: `.gafus-refactoring/architecture-qa-20261103-local/qa/chat2-stale-jwt-reconnect-negative.log`. The app token expires in 60 seconds; expiry bounds but does **not** eliminate this replay window. A subscribe proxy alone does **not** fix it: token-bearing subscriptions bypass the proxy. Evidence `.gafus-refactoring/architecture-qa-20261103-local/qa/chat2-subscribe-proxy-stale-token-try.log`.

## Tested local design that fails closed

Use **both** mechanisms together (neither alone suffices):

1. **Signed connection JWT** remains user-scoped (`issuer=gafus-chat2`, HS256) and retains its current authorization. The Chat2 client uses proxy-only `newSubscription("chat2:" + roomId)` and sends **no room JWT**, including on reconnect/refresh.
2. For the broker's `chat2` namespace, enable server-side `channel.proxy.subscribe` to a **trusted internal HTTP endpoint**. For every subscribe/reconnect the backend re-runs the existing actor-scoped `readGate` against the current PG membership, direct-user blocks, specialist lane and course entitlements. A failed DB query MUST refuse the subscription, never fall back to static JWT.
3. Enable Centrifugo's *separate* `client.subscription_token` HMAC key, known only to the broker and **different** from the connection JWT key; the old room JWT signed by the connection key is therefore invalid even if a client deliberately supplies it to bypass the proxy. Do not reuse provider/production keys in tests.
4. Maintain the existing immediate `/api/unsubscribe` on ban/leave. It clears already-active sessions; server-side subscription authorization prevents old-JWT replay and permission-less reconnect.

The local QA runner uses random loopback ports, memory broker, generated synthetic credentials, a separate subscription key, a temporary authenticated PostgreSQL 18 + Redis, and an HTTP proxy using the **actual** `readGate` and the new pure Core `authorizeChat2SubscriptionProxy` adapter. Config is built only in its own disposable directory. No fixed foreign port `8039`, existing Postgres/Redis data, production S3/CDN, or external broker were accessed. `Centrifugo v6.9.7+dirty` is a *pinned local binary*, not proof of a verified production image digest.

Local E2E: `node ci-cd/scripts/local-chat2-queue.realpg.mjs --realtime-ws` and `apps/api/tests/chat2-realtime-centrifugo.realpg.archqa.acceptance.ts`, with `apps/api/vitest.archqa-realtime-ws.config.ts`. The positive checks include authenticated delivery from actual PG outbox through Redis/Centrifugo/WebSocket, ordinary reconnect, BAN-caused live unsubscribe, proxy denial of banned reconnect, rejection of old signed room JWT, and actor/room validation. The corresponding Core policy is in `packages/core/src/services/chat2/subscribeProxyPolicy.ts` (no Prisma import, transport-specific authorization injected).

## Review-ready GAFUS integration (2026-11-04, **local only**)

The original isolated demonstration has now become a **real application implementation**, still inactive by default:

- `apps/api/src/app.ts` mounts `/internal/chat2/chat2-subscribe` **only when** `CHAT2_SUBSCRIBE_PROXY_ENABLED=true`. Invalid/missing `CHAT2_SUBSCRIBE_PROXY_SHARED_SECRET` (minimum 32 characters) fails startup or token mode validation; with the default disabled, this endpoint is absent.
- `apps/api/src/modules/chat2/subscribeProxy.ts` is the real Hono handler: max 8192 bytes, application/json-only, SHA256 constant-time broker shared-secret comparison (`X-GAFUS-Subscribe-Proxy-Key`), `private,no-store`, generic errors. It delegates every subscription to Core `authorizeChat2SubscriptionProxy(...)` and the live `readGate` (member/ban, two-way direct blocks, specialist restrictions, course ACL). Missing broker identity or DB/ACL failure never grants permission. The proxy is NOT a cookie/JWT end-user endpoint.
- `apps/api/src/modules/chat2/realtime.ts` extends `/api/v1/chats/realtime/connect` with the **optional** `subscriptionMode:"proxy"` only when explicitly enabled with a broker secret. Without the flag, the response retains **exactly** `{token,wsUrl}`; existing `GET /:id/realtime` JWT response stays present for old clients. The broker must reject old room JWTs via a **different** subscription signing key in proxy-only mode.
- `packages/core-client/src/chat2/realtimeSubscription.ts` is the single shared handshake for `apps/web-vite/src/features/chats/Chat2Messenger.tsx` and `apps/mobile/src/features/chat2/Chat2RoomScreen.tsx`: the *server* selects the mode. In `proxy`, neither client requests `/realtime` nor puts a token into `newSubscription`, including reconnections. In legacy/missing mode both clients retain signed room JWT and token refresh. Both UI states now mark `online/live` on **successful room subscription**, not merely socket connection; `unsubscribed` switches to the existing HTTP polling fallback (12s).
- `infra/chat2/centrifugo.proxy-only.review.json` is a **separate review-only** Centrifugo v6.9.7 config template: `chat2` subscribe proxy to `/internal/chat2/chat2-subscribe`, broker static shared-auth header, **separate** `client.subscription_token.hmac_secret_key`, connection JWT issuer, existing recovery/history settings, and explicit placeholders. Neither `infra/chat2/centrifugo.prod.json` nor `ci-cd/docker/docker-compose.prod.yml` references this template. The isolated runner loads this **same reviewed JSON**, substitutes random synthetic secrets/ports, uses `centrifugo checkconfig --strict`, then launches only its own broker.

**Observed real-path acceptance**: `node ci-cd/scripts/local-chat2-queue.realpg.mjs --realtime-ws` passed `6/6` on a new disposable PG18 + Redis + Centrifugo 6.9.7; the test **imports the real** `apps/api/src/app.ts` and HTTP routes through `/internal/chat2/chat2-subscribe`, not a test proxy factory. It tests authenticated actual `/api/v1/chats/realtime/connect` negotiation (`subscriptionMode:"proxy"`) and the unchanged room token HTTP response, unauthenticated forged subscribe POST (`403`), legitimate live subscribe, actual message DB outbox → WebSocket, reconnect, immediate BAN → `/api/unsubscribe`, rejection of a previously issued room JWT by the broker's *distinct signing key* and refusal of a fresh proxy-only subscription by the mounted Hono endpoint's current DB ACL. The proxy outage test proves **no permission when it is offline**, and successful reconnection after recovery. Latest log: `.gafus-refactoring/architecture-qa-20261103-local/qa/chat2-review-ready-full-real-HTTP-JWT-ACL.log`, later negative-assertion recheck in `final-real-ws-banned-replay-after-review-ready.log`.

`node --test ci-cd/scripts/chat2-proxy-cutover.contract.test.mjs` checks broker template, inactive production compose, both client branches and explicit server opt-in. ## Compatibility, operational review and **not-yet-approved** activation

**Safe migration path**: (1) ship Web/Mobile capable of the additive connection response, while `CHAT2_SUBSCRIBE_PROXY_ENABLED` remains off; (2) verify internal-only broker→Hono network ingress, static header injection by broker rather than client, separate secrets/rotation, per-subscription rate and API health alerts; (3) explicitly configure and validate the new broker namespace/proxy with the reviewed template and its *distinct* subscription HMAC key; (4) only then enable `CHAT2_SUBSCRIBE_PROXY_ENABLED=true` on the API and check old and new app versions. Never enable an old JWT-signing key as the new subscription key; that would reopen the proven stale-token replay.

**Previous Web/Mobile binaries are API-compatible but not guaranteed realtime-compatible after cutover:** they may still request the legacy `/:id/realtime` JWT, which the correctly separated Centrifugo signing key must refuse. Their existing 12-second HTTP polling preserves message retrieval, but websocket `live` will be unavailable until upgrade. This is an explicit deployment trade-off, not zero-downtime websocket parity. New clients preserve legacy behavior when the server does not advertise `proxy`.

**Rollback decision:** if the new broker proxy fails, disable realtime/keep authenticated HTTP polling while investigating; **do not** silently re-accept old 60s room JWTs, which would restore the demonstrated banned-user replay window. Actual production rollback/release, Nginx path protection, live monitoring, secret issuance, mobile version cohort rollout and Cloud deployments require separate approval; none were executed here.

No production configuration, live authentication keys, Git push, deployed broker, existing database, or application migration journal was modified while producing this candidate.

## 2026-11-05: Владелец утвердил ОБЯЗАТЕЛЬНЫЙ proxy-only, без старой схемы

**Этот блок — актуальный статус и заменяет приведённый выше переходный сценарий с JWT fallback.** Пользователь прямо решил **принудительно обновить все Mobile** и полностью исключить legacy Chat2 room JWT. Никакого смешанного режима Web/Mobile, никакой серверной выдачи `/:id/realtime` и никакого старого токена для повторного входа после BAN.

**Реализовано локально:** `packages/core-client/src/chat2/realtimeSubscription.ts` — только `proxy`, нет `token`/`getToken`/legacy grant; `apps/api/src/modules/chat2/realtime.ts` — `503` без `CHAT2_SUBSCRIBE_PROXY_ENABLED=true`/секрета, только connection JWT с `subscriptionMode:"proxy"`; `apps/api/src/routes/v1/chats.ts` — удалён room JWT route; оба клиентов и их API удалили request/refresh комнатных JWT. Centrifugo production/local config и Compose — приватный broker→Hono subscribe proxy, **never-issued отдельный** subscription JWT verification key, отключение прямого клиентского подписания, четыре независимых секрета. Внешние `gafus.ru`, Vite и **отдельный `api.gafus.ru`** deny broker subscribe ingress; API host сохраняет защищённые Cloud.ru media job callbacks. При BAN и DM block запрет сначала коммитится в БД, затем брокер отключает уже существующую подписку, чтобы не было reentry между unsubscribe и BAN.

**Мобильный cutover:** `apps/api/src/lib/chat2-mobile-version-gate.ts` даёт HTTP `426` для устаревшей/некорректной Mobile-версии на всех `/api/v1/chats/*`, либо `503` без правильного platform minimum; Web путь не зависит от заголовка версии. CI/release gates требуют store attestations для **обеих** платформ `CHAT2_MOBILE_STORES_VERIFIED=true`, опубликованные фактические `CHAT2_MOBILE_IOS_MIN_VERSION` и `CHAT2_MOBILE_ANDROID_MIN_VERSION` **строго больше `1.7.2`**; `--candidate` и `--release` сравнивают их с реальным публичным policy в read-only запросе; первый gate срабатывает до потенциальных deploy-операций. GitHub vars/secrets **не создавались** и публикуемые версии неизвестны — нельзя выставлять наугад. До публикации сборок production cutover должен быть заблокирован. Старыми сборками допускается получать публичный config для экрана принудительного обновления, но Chat2 должен отказать даже если клиентский экран загрузки config дал сбой. Хедеры версий не являются авторизацией и не заменяют `readGate`.

**Подтверждение:** локальный actual PostgreSQL18 + Redis + Centrifugo6.9.7 E2E **6/6 exit0** повторён после удаления старого room JWT route; всё тестовое удалено. New Core-client **14/14**, API realtime/proxy/version **37/37**, cutover/source release **19/19** — PASS. Centrifugo production JSON `checkconfig --strict` с синтетическими переменными — PASS. Подробная инструкция и конкретный порядок релиза — `docs/operations/chat2-proxy-only-forced-mobile-cutover-20261105.md`. Никакого production/access, push, release, реальных секретов/баз/сторов не меняли. **No old JWT fallback is permitted as rollback.**
