**Человек и Admin Panel**

В админке задаются:

какие сайты подключены;
какие аккаунты используются;
какие действия можно выполнять автоматически;
какие действия требуют подтверждения человека;
куда отправлять отчёты.

например 
Название: WB заказы утром
Сайт: Wildberries Seller
Ссылка: https://seller.wildberries.ru
Аккаунт: wb_account_1
Что сделать: собрать данные по заказам
Когда запускать: каждый день в 09:00
Включено: да

тыкаем сохранить. -> регистрирует repeatable job в BullMQ и сохраняет всё в бд.

**Планировщик задач**

BullMQ видит что подъехало время какой-то задачи и создаёт обычную job.
   ↓
BullMQ записывает эту job в Redis
   ↓
Worker через BullMQ читает эту job из Redis

BullMQ отвечает за очередь:
- создать job по расписанию
- положить job в Redis
- выдать job свободному worker
- отметить job completed / failed
- сделать retry, если worker выбросил ошибку
- хранить статус job

## BullMQ и Redis

**Worker / Оркестратор**

Отвечает за выполнение сценария:
- получить job из BullMQ
- прочитать taskConfigId из job
- загрузить config из БД через Prisma
- понять:
  - какой сайт нужен
  - какой сценарий нужен
  - какой аккаунт использовать
  - с какого URL начинать
- взять доступы аккаунта из защищённого хранилища
- выбрать подходящую Windows VM
- подключиться к Browser Agent внутри этой VM
- выбрать нужный браузерный профиль
- выбрать нужный Site Adapter
- запустить выполнение сценария через Site Adapter
- получать от Site Adapter статус выполнения
- сохранять данные, файлы, логи, скриншоты и видео
- при ошибке собрать observation через Browser Agent
- при нестандартной ситуации обратиться к AI Agent Core
- проверить предложение AI Agent Core по правилам безопасности
- либо выполнить безопасное recovery-действие
- либо поставить задачу на паузу и позвать человека
- завершить job как completed / failed / waiting_for_human

   ↓ HTTP/gRPC/WebSocket

   ↓

**AI Agent Core**

AI Agent Core используется не как основной исполнитель сценария, а как слой анализа нестандартных ситуаций. Основной сценарий выполняется детерминированно через Site Adapter, а LLM подключается только если обычный сценарий не смог продолжиться.

Когда вызывается LLM:
- не найден ожидаемый элемент;
- изменилась верстка или текст кнопок;
- появился неизвестный попап;
- страница выглядит не так, как ожидалось;
- изменилась структура таблицы или отчёта;
- файл не скачался или скачался не тот файл;
- истекла сессия;
- появился security challenge, CAPTCHA или 2FA;
- нужно сформулировать понятное объяснение для отчёта.

AI Agent Core получает от Worker не доступы и не управление браузером, а только observation:
- текущий URL;
- title страницы;
- видимый текст;
- список интерактивных элементов;
- accessibility tree;
- скриншот при необходимости;
- последние действия агента;
- цель текущего шага сценария;
- ошибку, из-за которой сценарий остановился.

После анализа LLM возвращает структурированный результат, например:
- тип проблемы: `popup`, `selector_not_found`, `layout_changed`, `auth_required`, `captcha_required`, `download_failed`;
- краткое объяснение;
- предлагаемое recovery-действие;
- уровень риска;
- confidence.

LLM не выполняет действие сам. Worker проверяет предложение по правилам безопасности: разрешено ли такое действие в сценарии, есть ли элемент на странице, не затрагивает ли действие деньги, цены, поставки, юридические подтверждения или персональные данные. Только после этой проверки Browser Agent может выполнить безопасное действие.

Примеры безопасных действий:
- закрыть информационный попап;
- повторить шаг;
- обновить страницу;
- перейти назад;
- нажать похожий элемент, если он совпадает по смыслу и находится в разрешённой зоне сценария;
- проверить папку загрузок;
- остановить задачу и позвать человека.

**Модуль конкретного сайта / Site Adapter**
Site Adapter — это модуль кода, который знает, как работать с конкретным личным кабинетом.
Новый веб-сервис подключается через отдельный Site Adapter: в нём описываются разрешённые сценарии, проверки результата и ограничения по действиям. 

WildberriesAdapter знает Wildberries Seller
OzonAdapter знает Ozon Seller
AvitoAdapter знает Avito

Содержит детерминированные сценарии.
Например для Wildberries:
scenario = collect_orders

WildberriesAdapter знает:
1. открыть seller.wildberries.ru
2. проверить, что пользователь залогинен
3. перейти в раздел заказов
4. выбрать нужный период
5. скачать или прочитать данные
6. проверить, что данные получены
7. вернуть результат Worker'у

ВАЖНО
Site Adapter сначала работает без LLM.
Он выполняет понятный заранее сценарий обычным кодом.

Если сценарий сломался:
- кнопка не найдена
- верстка изменилась
- появился странный попап

тогда Worker собирает observation и обращается к AI Agent Core.


**Windows-браузерный агент на Playwright**
Обычный программный слой, который управляет браузером. 
Его задача — выполнять команды от Worker / Site Adapter и возвращать состояние браузера.
Собирает 
- текущий URL
- title страницы
- видимый текст
- список кнопок, ссылок и полей
- accessibility tree
- важные DOM-фрагменты
- скриншот
- ошибки консоли
- network errors
- информацию о скачанных файлах
- последнее выполненное действие

Если что-то пошло не так:
в LLM отправляет сжатое состояние через Worker:
URL
+ видимый текст
+ интерактивные элементы
+ скриншот, если нужно
+ последние действия
+ цель задачи


**Хранилище доступов** 
Отдельный компонент хранения
- логины
- пароли (не от админки, а к ВБ)
- cookies
- session tokens
- данные браузерного профиля

## Доступы храним в защищённом хранилище: Secrets Manager / Vault (должны быть обратимо зашифрованные)
Браузерный агент получает доступ только на время выполнения задачи.

Пароль пользователя нашего сервиса храним как hash, без возможности расшифровать. Они не относятся к Хранилище доступов.

**Xранилище артефактов**
Там лежат:
- скриншоты
- видео сессий
- скачанные отчёты
- HTML/DOM snapshots
- observation JSON


**Report Generator**
Он берёт данные из БД, логи и результаты задач, а LLM может помочь красиво сформулировать текст.

**Human Review**
Отвечает за:
-CAPTCHA;
-2FA;
-непонятных попапов;
-опасных действий;
-ручного продолжения зависшей сессии.

Вместо этого используется стабильная и проверяемая среда:

- обычный Chrome/Edge;

Если сайт показывает CAPTCHA, 2FA или security challenge:

2. Worker собирает observation.
3. AI Agent Core классифицирует ситуацию: `captcha_required`, `two_factor_required`, `security_challenge`.
4. Worker ставит задачу на паузу.
5. Задача уходит в Human Review Console.
6. Человек вручную подтверждает вход или решает CAPTCHA.
7. После этого Worker продолжает сценарий с того же места, если это безопасно.


## Стек технологий

- **Next.js + TypeScript** — админка и API для управления задачами.
- **PostgreSQL + Prisma** — хранение конфигов, запусков, статусов, логов и ссылок на артефакты.
- **BullMQ + Redis** — расписание, очередь задач, retry, backoff и статусы job.
- **Node.js + TypeScript Worker** — orchestration layer, потому что вся бизнес-логика и интеграции остаются в одном языке.
- **Windows VM + Chrome** — среда похожа на обычное рабочее место пользователя.
- **Playwright** — управление браузером, роли/селекторы, ожидания, trace, screenshots, downloads.
- **Vault / Secrets Manager** — защищённое хранение логинов, паролей, cookies и session tokens.
- **S3 / MinIO** — хранение тяжёлых артефактов: видео, скриншотов, скачанных файлов и snapshots.
- **OpenTelemetry / structured logs** — аудит действий, диагностика ошибок и сбор ежедневных отчётов.

Как это всё связано между собой

1. Worker получил job из BullMQ.

2. Worker прочитал taskConfigId из job.

3. Worker загрузил config из БД.

4. Worker понял:
   - site = wildberries
   - scenario = collect_orders
   - account_id = wb_account_1
   - start_url = https://seller.wildberries.ru

5. Worker взял доступы аккаунта из Хранилища доступов.

6. Worker выбрал нужный Site Adapter.
   Например:
   - site = wildberries
   - значит нужен WildberriesAdapter

7. Worker подключился к Browser Agent внутри Windows VM.

8. Browser Agent открыл Chrome с нужным браузерным профилем.

9. Browser Agent перешёл на start_url.

10. Site Adapter начал выполнять основной сценарий детерминированно:
   - проверить, что пользователь залогинен
   - перейти в нужный раздел
   - найти нужные кнопки/поля
   - нажать нужные элементы
   - скачать или прочитать данные
   - проверить результат

11. Если всё прошло штатно:
   - Site Adapter возвращает success
   - Worker сохраняет данные
   - Worker сохраняет логи, скриншоты, видео, скачанные файлы
   - Worker помечает BullMQ job как completed
   - результат попадает в ежедневный отчёт

12. Если Site Adapter столкнулся с нестандартной ситуацией:
   - не найдена ожидаемая кнопка
   - кнопка переехала или была переименована
   - появился неизвестный попап
   - изменилась верстка
   - истекла сессия
   - нужен повторный вход
   - появилась CAPTCHA или 2FA
   - произошёл таймаут
   - файл не скачался
   - данные выглядят странно

13. Browser Agent собирает observation:
   - текущий URL
   - title страницы
   - видимый текст
   - список кнопок, ссылок и полей
   - accessibility tree
   - важные DOM-фрагменты
   - скриншот
   - ошибки console/network
   - последнее выполненное действие
   - на каком шаге сценария произошёл сбой

14. Worker передаёт observation в AI Agent Core.

15. AI Agent Core не управляет браузером напрямую.
   Он анализирует ситуацию и возвращает диагноз.

   Например:
   - popup
   - selector_not_found
   - button_moved
   - layout_changed
   - auth_required
   - captcha_required
   - timeout
   - download_failed
   - unknown_error

16. AI Agent Core может предложить безопасное recovery-действие.

   Например:
   - close_popup
   - click_similar_element
   - retry_step
   - refresh_page
   - go_back
   - recheck_downloads
   - ask_human
   - stop_task

17. Если проблема в том, что кнопка переехала или была переименована:
   - AI Agent Core ищет похожий элемент по тексту, смыслу, accessibility tree или скриншоту
   - например ожидаем “Заказы”
   - а на странице есть “Заказы и продажи”
   - AI предлагает попробовать новый элемент

18. Worker проверяет предложение AI Agent Core по правилам:
   - есть ли такой элемент на странице
   - разрешено ли это действие
   - низкий ли риск
   - достаточно ли confidence
   - не влияет ли действие на деньги, цены, поставки или юридически значимые операции
   - не требует ли действие подтверждения человека
   - не превышен ли лимит recovery-попыток

19. Если действие безопасное:
   - Worker отдаёт команду Browser Agent
   - Browser Agent выполняет действие
   - Site Adapter валидирует результат

20. Site Adapter проверяет:
   - попали ли мы на нужную страницу
   - появились ли ожидаемые данные
   - можно ли продолжать основной сценарий

21. Если проверка успешна:
   - Site Adapter продолжает сценарий с места сбоя
   - задача выполняется дальше

22. Если проверка неуспешна:
   - Worker логирует неудачную recovery-попытку
   - при необходимости пробует другой безопасный вариант
   - после лимита попыток ставит задачу на паузу

23. Если действие небезопасное или непонятное:
   - Worker не выполняет его автоматически
   - сохраняет скриншот, видео, observation и причину
   - создаёт human review task
   - job получает статус waiting_for_human или failed

24. Если появилась CAPTCHA или 2FA:
   - AI Agent Core только классифицирует ситуацию
   - Worker ставит задачу на паузу
   - создаёт human review task
   - человек вручную подтверждает вход или решает CAPTCHA
   - после этого Worker может продолжить сценарий

25. В конце:
   - при успехе job = completed
   - при ошибке job = failed
   - при ожидании человека job = waiting_for_human
   - все события сохраняются в логи
   - данные и файлы сохраняются в хранилище
   - итог попадает в ежедневный отчёт

Где LLM, а где детерминированная логика

Детерминированная логика используется там, где важны повторяемость и контроль:
- загрузка конфига;
- выбор аккаунта, профиля и VM;
- запуск браузера;
- выполнение основного сценария через Site Adapter;
- работа с файлами;
- retry;
- статусы задач;
- валидация результата;
- правила безопасности;
- любые опасные действия.

LLM используется там, где нужна интерпретация:
- понять, что изменилось на странице;
- классифицировать неизвестный попап;
- найти похожий элемент по тексту, смыслу или accessibility tree;
- объяснить причину сбоя;
- предложить безопасное recovery-действие;
- написать человеческий текст для отчёта.

Такой раздел нужен, чтобы LLM не превращался в неконтролируемого исполнителя. Он анализирует и предлагает, а Worker проверяет и принимает решение по правилам.
