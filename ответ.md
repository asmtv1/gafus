мы меняем логику работы Site Adapter. 
Теперь в нём заложены более абстрактные вещи. 
т.е. он перестаёт быть набором Playwright-селекторов и становится модулем бизнес-сценариев конкретного сайта.
Site Adapter знает:
- какие данные нужны для сценария;
- какие источники доступны;
- в каком порядке их пробовать;
- как проверить полноту и корректность результата.

Можно взять из официального API? Берём из API. (не понимаю пока почему у вас "fallback на API", API-first звучит надёжнее, а что с ручки не получили уже добиваем как можем (fallback на выгрузки/UI). Возможно, в прикладном плане я чего-то не улавливаю пока.)
Можно скачать стабильную выгрузку из кабинета? Через Browser Engine скачиваем файл и парсим его кодом.
Нужен UI? Через Browser Engine читаем UI/DOM/экран.
Если появляется CAPTCHA, 2FA или security challenge, задача ставится на паузу и уходит человеку.

Browser Engine
Выбирает только технический способ взаимодействия с сайтом (разные providers).

Конкретный provider вы бираем по конфигу, состоянию аккаунта и результатам предыдущих запусков.
1. Обычный Chrome + Playwright. (если всё стабильно)
2. Обычный Chrome, но с постоянным браузерным профилем.
3. Антидетект-профиль
Когда обычный Chrome + Playwright нестабилен из-за признаков автоматизации. 
4. RPA/visual управление
работает не через DOM-селекторы, а через экран: получает скриншот, распознаёт элементы по тексту/картинке/OCR, двигает мышь, нажимает клавиши и проверяет результат.
      
обмен всем этим через Worker
Worker
  -> Site Adapter
       -> возвращает execution plan / next step
  -> Worker исполняет:
       -> API Client
       -> Browser Engine
       -> Export Parser
       -> Data Merger
       -> Human Review

Если сценарий что часть данных нужно через API, а часть через Browser Engine то
Worker
  -> Site Adapter
      -> шаг 1: получить часть данных через API
      -> шаг 2: получить часть данных через Browser Engine
      -> шаг 3: нормализовать данные
      -> шаг 4: склеить по понятным ключам
      -> шаг 5: проверить полноту результата

Перед разработкой проверяем жизнеспособность:

1. Выписываем все нужные данные и действия по макрету.
2. Отмечаем, что можно получить через официальный API.
3. Отмечаем, что можно получить через выгрузки из кабинета.
4. Проверяем обычный Chrome + Playwright на тестовом аккаунте.
5. Проверяем работу через сохранённый профиль после ручного входа.
6. Отдельно проверяем RPA/visual provider:
   - может ли он находить нужные кнопки по OCR/тексту/картинке;
   - может ли пройти сценарий без DOM-селекторов;
   - насколько он зависит от разрешения экрана, масштаба Windows и языка интерфейса;
   - насколько он медленнее обычного Playwright;
   - как часто всё равно требуется человек.
7. Несколько дней погонял бы сценарий по расписанию и замерил:
   - сколько запусков успешны;
   - как часто слетает сессия;
   - как часто появляется CAPTCHA/2FA;
   - где именно ломается UI;
   - какие данные не удаётся получить.
8. После этого выбрал рабочую стратегию: API, выгрузки, браузер, RPA/visual, ручной режим или комбинация.
